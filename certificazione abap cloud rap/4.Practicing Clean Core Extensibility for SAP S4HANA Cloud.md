Evaluating the Need for Extensions
Cos’è un’Estensione Software?

Iniziamo la nostra discussione sulle estensioni esaminando il termine estensione. Cos’è un’estensione? Cosa stiamo esattamente estendendo? E, soprattutto, perché la stiamo estendendo?
Tutto il software è progettato con un ambito in mente. Questo ambito definisce due cose:
    • Il risultato per il cliente che il software fornisce
    • Come il software fornisce quel risultato
Dal punto di vista del cliente, è il raggiungimento dei risultati a creare valore. Per un fornitore di software come SAP, l’ambito è la base della proposta di valore presentata al cliente ed è una parte critica del processo di progettazione del software.
Senza dubbio, uno dei maggiori vantaggi storici di SAP ERP è stato proprio il suo ambito. Fornire un prodotto concepito per coprire praticamente tutti i processi aziendali nelle aree logistica, finanza e risorse umane è un compito enorme. Considerando che la base clienti di SAP copre oltre 30 settori industriali diversi, la portata del compito diventa ancora più chiara. Ogni settore ha modalità specializzate per eseguire determinati processi aziendali (ad esempio, le banche possono progettare ed eseguire i processi di approvvigionamento in modo diverso rispetto a un ente governativo o militare) e, anche all’interno dello stesso settore, le singole aziende possono progettare ed eseguire un processo in modo diverso. Ma la sfida dell’ambito non è mai stata evitata da SAP; al contrario, è stata affrontata con entusiasmo.
La necessità di flessibilità
Mentre l’ampiezza dell’ambito coperto dalle applicazioni SAP è senza dubbio un fattore importante per i clienti nell’adottare le soluzioni SAP, c’è un altro fattore che essi apprezzano: la flessibilità, ossia la capacità di adattare l’ambito fornito per soddisfare le proprie esigenze uniche. Di conseguenza, si presentò a SAP un’altra sfida: come non solo fornire ambito ai clienti, ma anche flessibilità per adattarlo alle loro esigenze specifiche? Come per l’ambito, SAP affrontò la sfida della flessibilità con entusiasmo. Tuttavia, affrontare questa sfida richiese un certo “pensiero progettuale fuori dagli schemi”.
Una possibile soluzione avrebbe potuto essere quella di fornire al cliente un sistema in cui, una volta installato e attivo, il codice sorgente fosse “congelato”. Il cliente non avrebbe avuto la possibilità di modificare o cambiare quel codice, e si sarebbe dovuto occupare solo della manutenzione ordinaria, aggiornamenti e upgrade – tutti per lo più semplici e indolori. Il reparto IT responsabile della manutenzione del sistema avrebbe semplicemente applicato la patch pertinente o, al momento opportuno, aggiornato il software. Successivamente, avrebbe eseguito un rapido test per assicurarsi che tutto funzionasse correttamente. Sebbene dal punto di vista dell’usabilità questa soluzione sarebbe stata apprezzata dall’IT, i business stakeholder e soprattutto gli utenti finali (dove il vero valore del sistema software si realizza) probabilmente non lo sarebbero stati, poiché entrambi richiedono un software più flessibile per quanto riguarda gli adattamenti. È inutile dire che questo approccio non fu adottato da SAP.
Un’altra possibile soluzione risiedeva all’estremo opposto dello spettro: un sistema fornito con un repository di codice di base, ma in cui quel codice fosse una “suggestione”. Il sistema sarebbe stato completamente aperto. Modifiche, cambiamenti e cancellazioni totali del codice sarebbero stati permessi. In un ambiente del genere, anche il più semplice rilascio di manutenzione da parte di SAP (solo applicando una patch tecnica per correggere un bug) sarebbe stato carico di incertezze. Avrebbe potuto richiedere mesi applicare una patch che normalmente richiederebbe pochi minuti. Un upgrade completo sarebbe stato un incubo. A seconda dell’ambito del cliente, i cambiamenti effettuati durante un semplice upgrade avrebbero potuto richiedere anni. I costi associati a questo approccio erano notevoli, sia per SAP sia per il cliente. Oltre ai costi finanziari derivanti dalle ore di IT dedicate a compiti operativi che dovrebbero essere semplici, c’erano anche costi opportunità dovuti all’incapacità del sistema di rispondere rapidamente a un mercato che richiede adattabilità. Come per il primo approccio, neanche questo fu adottato da SAP.
Ciò che era necessario era l’approccio “Goldilocks”, dove i bisogni dei seguenti tre gruppi distinti fossero bilanciati:
    • Utenti finali, che vogliono un software con un’esperienza utente coerente (di cui parleremo in una lezione successiva), semplice e facile da usare.
    • Business stakeholder (in particolare i process owner), che vogliono un’applicazione stabile ma che possa essere personalizzata per eseguire i processi aziendali secondo le loro modalità desiderate.
    • Reparto IT, che deve installare e mantenere un sistema, soddisfacendo i bisogni dei due gruppi sopra, ma in cui i costi siano gestiti in maniera ottimale per l’azienda.
Questo approccio ha dato origine agli aggiustamenti di codice iniziati dal cliente. Il sistema veniva installato con funzionalità standard (basate sulle best practice), ma anche con la possibilità per il cliente, in modo chiaro e controllato, di adattare quella funzionalità per ottenere risultati desiderati coerenti con le esigenze degli stakeholder in maniera economica.
Sebbene inizialmente questo approccio possa sembrare inevitabile, è facile dimenticare che decenni fa, quando SAP R/3 fu introdotto sul mercato, fu considerato rivoluzionario. Tuttavia, si può affermare che nel tempo questo approccio bilanciato sia diventato uno dei fattori più importanti nel fenomenale successo di SAP ERP.

Evaluating the Need for Extensions — Exam Summary
What Is a Software Extension?
Definition of an Extension
    • A software extension is a controlled way to adapt delivered standard software.
    • An extension modifies how results are achieved, not what value the software provides.
    • Extensions exist because standard software is designed with a defined scope.
Software Scope
    • Scope defines:
        ◦ The business outcome delivered to the customer
        ◦ The implementation approach used to deliver it
    • For SAP, scope is a core element of its value proposition.

SAP ERP Scope — Why Extensions Are Necessary
Breadth of SAP Scope
    • SAP ERP covers:
        ◦ Logistics
        ◦ Finance
        ◦ Human Resources
    • SAP customers span 30+ industries, each with:
        ◦ Industry-specific processes
        ◦ Company-specific variations
Consequence of Broad Scope
    • A single standard cannot fully satisfy all customers.
    • Even within the same industry, processes differ.
    • Therefore:
        ◦ Standardization alone is insufficient
        ◦ Flexibility becomes mandatory

The Need for Flexibility
Customer Expectations
    • Customers value:
        ◦ Wide functional coverage
        ◦ Ability to adapt processes to their needs
    • Flexibility is as important as scope.
SAP’s Core Challenge
    • How to provide:
        ◦ A stable, upgradable system
        ◦ Without blocking customer-specific adaptations

Extreme Approaches SAP Did NOT Choose
Fully Frozen System
    • Characteristics:
        ◦ No customer code changes allowed
        ◦ Easy maintenance and upgrades
    • Problems:
        ◦ Business stakeholders cannot adapt processes
        ◦ End users lose flexibility
    • Outcome:
        ◦ ❌ Rejected by SAP
Fully Open System
    • Characteristics:
        ◦ Core code freely modifiable
        ◦ No separation between standard and custom
    • Problems:
        ◦ Patches and upgrades become risky and slow
        ◦ High IT and opportunity costs
    • Outcome:
        ◦ ❌ Rejected by SAP

The “Goldilocks” Approach to Extensions
Balanced Design Goal
SAP designed an approach that balances the needs of:
    • End users
        ◦ Consistent, simple user experience
    • Business stakeholders
        ◦ Stable but adaptable business processes
    • IT departments
        ◦ Maintainable systems with controlled costs
Resulting Extension Model
    • System is delivered with:
        ◦ Standard functionality based on best practices
        ◦ Clearly defined, controlled extension points
    • Customers can:
        ◦ Adapt behavior
        ◦ Preserve upgradeability
        ◦ Control long-term costs

Historical Impact
Customer-Initiated Adjustments
    • Extensions enabled customers to:
        ◦ Achieve desired outcomes
        ◦ Without breaking the standard core
    • This model:
        ◦ Was revolutionary with SAP R/3
        ◦ Became a key success factor of SAP ERP

Key Exam Takeaways
What You Must Recognize Instantly
    • Extensions exist to balance scope and flexibility
    • SAP rejected both:
        ◦ Fully frozen systems
        ◦ Fully open systems
    • SAP’s success is rooted in:
        ◦ Controlled extensibility
        ◦ Clear separation between standard and custom
Typical Exam Traps
    • ❌ Thinking extensions exist only for technical reasons
    • ❌ Assuming full source code freedom is desirable
    • ❌ Ignoring the role of IT cost and upgradeability
    • ✅ Recognizing extensibility as a strategic design choice

Introducing the Clean Core Approach
Approcci classici di estendibilità

Nel mondo precedente al cloud, questo approccio era sotto molti aspetti piuttosto semplice da implementare sia per SAP sia per il cliente. In alcuni aspetti, era simile a un contratto. C’erano certe funzionalità che SAP forniva e certi passaggi e procedure che i clienti seguivano. Immaginiamo uno scenario semplice in cui uno schermo di un’applicazione SAP contiene due campi: ricavi e costi. Non sarebbe troppo presuntuoso ipotizzare che un utente finale richieda l’aggiunta di un campo supplementare alla visualizzazione. Supponiamo che lo faccia richiedendo un nuovo campo per visualizzare il profitto. E supponiamo che il profitto venga calcolato non solo utilizzando ricavi e costi, ma anche un fattore numerico speciale utilizzato dal cliente. Poiché questo fattore è specifico del cliente, non esiste un campo per contenerlo in nessuna delle tabelle di database sottostanti utilizzate dall’applicazione.
Per implementare questo tipo di scenario, SAP forniva ai clienti quelli che erano conosciuti come exits. Queste exits erano collocate su più livelli dello “stack”. Analizziamo questi livelli uno per uno, iniziando dal livello più basso: il livello dei dati. Nel nostro scenario semplice, uno sviluppatore avrebbe utilizzato un table append per aggiungere un nuovo campo a una tabella di database rappresentante il fattore numerico menzionato precedentemente. Una volta attivato, questo campo sarebbe stato disponibile sia per la lettura sia per la memorizzazione. Il table append forniva ai clienti un concetto di exit universale per adattare la definizione di qualsiasi tabella SAP fornita alle loro esigenze aziendali uniche.
Il livello successivo dello stack che necessitava di un exit fornita da SAP era il più alto: il livello visivo. È qui che il nuovo campo (profitto, nel nostro scenario semplice) sarebbe stato visualizzato. Le visual layer exits consistevano principalmente in due tipi: screen exits e menu exits. Nel nostro scenario semplice, uno sviluppatore avrebbe utilizzato una screen exit per aggiungere il nuovo campo allo schermo e possibilmente una menu exit per aggiungere un nuovo comando che, una volta selezionato dall’utente finale, avrebbe eseguito il calcolo del profitto.
Il livello finale dello stack che necessitava di un exit sarebbe in qualche modo stato il più importante. Questo perché un nuovo campo aggiunto al livello dati dello stack e visualizzato al livello visivo dello stack avrebbe contenuto un valore che avrebbe potuto dover essere letto, utilizzato, aggiornato e forse anche cancellato di tanto in tanto. Queste operazioni dovevano essere implementate utilizzando codice ABAP. Pertanto, SAP creava code exits implementate al livello intermedio (cioè codice) tra i dati e l’interfaccia utente. Ancora una volta, nel nostro scenario semplice, uno sviluppatore avrebbe prima confermato l’esistenza di una code exit per eseguire le operazioni necessarie sul campo e poi l’exit sarebbe stata implementata con il codice specifico del cliente.
Di conseguenza, il cliente avrebbe avuto la funzionalità standard fornita da un’applicazione, arricchita con le funzionalità aggiuntive desiderate. Un aspetto importante di questo approccio era che l’intero processo di utilizzo delle exits era gestito da un processo di sistema definito. Le exits dovevano essere attivate. L’implementazione specifica dell’exit doveva superare tutti i test rilevanti di sintassi e consistenza. Lo sviluppo delle exits avveniva in un sistema di sviluppo dedicato e veniva testato in un sistema di test prima di essere rilasciato agli utenti finali nel sistema di produzione. Un altro aspetto importante di questo approccio era che, generalmente parlando, lo sviluppo delle exits poteva utilizzare qualsiasi oggetto SAP nel sistema senza restrizioni. Per esempio:
    • Qualsiasi tabella SAP poteva essere utilizzata per leggere e scrivere record
    • Qualsiasi function module SAP poteva essere chiamato
    • Qualsiasi classe SAP (e i suoi metodi) poteva essere utilizzata
Un ultimo punto (e importante). Se un cliente determinava che nessuna exit era disponibile (o utilizzabile), poteva esercitare due scelte:
    1. Modificare gli oggetti SAP in modo da ottenere la funzionalità desiderata.
    2. Copiare gli oggetti SAP. Il nuovo oggetto sarebbe stato di proprietà del cliente e quindi modificabile di conseguenza.
Come menzionato in precedenza, un sistema che offre il beneficio degli aggiustamenti del cliente come parte del suo design deve bilanciare certi benefici e certi costi. In altre parole, quando arriva il momento di applicare patch o aggiornare il sistema, qualsiasi estensione implementata potrebbe teoricamente diventare un problema perché il codice nuovo o aggiornato dal fornitore software potrebbe rendere un’estensione instabile o persino inutile. Sarebbe necessario testare per assicurarsi che ciò non accadesse. Tuttavia, tenendo conto di questo, i costi di gestione del processo di test erano ragionevoli rispetto ai benefici e alla flessibilità delle estensioni. Generalmente parlando, gli aggiustamenti dei clienti fatti tramite implementazione di exits erano meno problematici durante gli upgrade, poiché l’esistenza delle exits era nota a SAP e poteva essere considerata. Modifiche agli oggetti SAP e/o copie degli oggetti SAP potevano essere molto più problematiche e dovevano essere testate accuratamente dopo l’applicazione di una patch o l’esecuzione di un upgrade.
Questo approccio ha sostenuto SAP e i clienti per molti decenni. Dalla SAP R/3 in tutte le sue versioni fino a SAP Business Suite, attraverso service pack ed enhancement pack. Tuttavia, una delle ragioni per cui questo approccio è stato efficace era che i sistemi erano quasi sempre situati nei data center dei clienti e quindi erano gestiti al 100% dai clienti stessi. Ciò che un cliente faceva nel proprio sistema era completamente separato da ciò che altri clienti facevano nei loro sistemi. Tuttavia, si è verificato un “game changer”. Questo cambiamento è stato l’evoluzione da SAP ERP a SAP S/4HANA.

Concetto di Clean Core

SAP S/4HANA Cloud funziona nel cloud, e un prodotto cloud è diverso. Tutti i clienti utilizzano la stessa linea di codice di base e le modifiche vengono applicate a tutti i clienti contemporaneamente. Di conseguenza, non esiste un modo realistico per consentire a ciascun cliente di implementare miglioramenti nello stesso modo in cui poteva farlo negli ambienti on-premise precedenti. Gli ampliamenti da parte del cliente sono ancora necessari, ma le regole e i processi con cui vengono eseguiti devono essere completamente ripensati e riprogettati per il mondo cloud. Entra qui un’altra sfida per SAP. Come le sfide precedenti, anche questa è stata affrontata da SAP.
La soluzione è progettare una filosofia di estensione distintamente orientata al cloud. Entra un nuovo termine: clean core. Analizziamolo.
Core
Il core descrive gli aspetti principali di SAP S/4HANA Cloud. Questi aspetti possono essere considerati come dimensioni o componenti e sono orientati attorno a quanto segue:
    • Processi: La serie di azioni o passaggi eseguiti all’interno di SAP S/4HANA Cloud che coprono l’esperienza end-to-end (E2E) di fornire un risultato o completare un obiettivo.
    • Dati: I dati contenuti all’interno e utilizzati dai processi di SAP S/4HANA Cloud. Comunemente categorizzati come configurazione, master e transazionali.
    • Integrazione: Connessione di SAP S/4HANA Cloud ad altre soluzioni al fine di inviare e ricevere dati a supporto dell’esecuzione dei processi.
    • Operazioni: Attività di manutenzione necessarie eseguite all’interno di SAP S/4HANA Cloud, come gestione delle release, gestione dei job in background, gestione delle autorizzazioni, monitoraggio e alerting.
    • Estendibilità: Funzionalità aggiunte a SAP S/4HANA Cloud per estenderlo e soddisfare esigenze organizzative non coperte dai processi standard.
Clean
Clean significa che per ciascuno degli aspetti precedentemente menzionati viene adottato l’approccio necessario affinché sia aggiornato, conforme al cloud, ottimizzato e perfezionato, a seconda dell’aspetto in questione.
Clean Core
Clean core è sia un concetto sia un approccio per ottenere un SAP S/4HANA Cloud moderno, flessibile e conforme al cloud. Il clean core si ottiene integrando ed estendendo SAP S/4HANA Cloud in modo conforme al cloud, con qualità ottimale dei dati master e governance dei processi aziendali perfezionata. Con un clean core, i clienti sperimentano una migliore manutenibilità, insieme a un minor costo totale di proprietà (TCO) di SAP S/4HANA Cloud.
Benefici del Clean Core
Il clean core avvantaggia tutti.
In sintesi, i benefici per i clienti sono:
    • Facilità di upgrade: rendere gli upgrade non problematici, dal punto di vista del codice personalizzato.
    • Rapida fruizione dell’innovazione: essere sempre aggiornati sulle tecnologie innovative.
    • Sicurezza, continuità e stabilità end-to-end del sistema.
    • TCO: utilizzo efficiente di infrastruttura e licenze.
    • Tracciabilità permanente in tutte le aree del core.
I benefici per i partner sono:
    • Soluzioni future-proof e pronte per il cloud.
    • Promuovere la conformità fit-to-standard con innovazione modulare del clean core.
    • Riduzione della complessità con consumo semplificato delle soluzioni SAP out-of-the-box.
Estendibilità Clean Core
Poiché questo percorso formativo tratta principalmente l’aspetto di estensione del clean core, questo sarà il focus della nostra discussione.
L’estendibilità del clean core può essere riassunta come una metodologia di estensione in cui le estensioni sono mantenute rigorosamente separate dall’applicazione SAP. Le estensioni accedono agli oggetti aziendali SAP solo tramite interfacce ben definite e stabili agli upgrade.
Nota la prima parte, “metodologia di estensione”. I clienti possono tirare un sospiro di sollievo: le estensioni non spariranno. Ma notate anche la seconda e la terza parte: l’estensione del cliente è mantenuta “rigorosamente separata” dal baseline SAP e deve utilizzare punti ufficialmente definiti che sono “stabili agli upgrade”. È proprio la parte “upgrade” a essere così importante. La disponibilità del sistema cloud non è solo una lista dei desideri per i clienti. È una richiesta non negoziabile. Non deve esserci alcuna possibilità che un sistema diventi non disponibile semplicemente perché è stata rilasciata una nuova versione del software. L’esistenza delle estensioni del cliente non altera questa aspettativa.
L’estendibilità clean core è il modo in cui si raggiunge l’equilibrio tra flessibilità del software con aggiustamenti del cliente e stabilità e disponibilità del sistema nel mondo cloud. Ciò comporta non solo un deployment del software più rapido, ma anche una più facile adozione delle modifiche software, poiché il core parte pulito e viene mantenuto tale tramite upgrade non distruttivi e regolarmente programmati.
Il concetto di estendibilità clean core può essere distillato in questo quadro di best practice adottate da un cliente nell’implementazione di SAP S/4HANA Cloud:
    • Adottare una politica di zero modifiche
    • Eliminare le estensioni ridondanti rispetto al codice e alla funzionalità standard ed eliminare anche le copie degli oggetti SAP
    • Utilizzare solo API rilasciate (“interfacce stabili agli upgrade”)
    • Sfruttare appieno l’estendibilità key user (in-app) di SAP S/4HANA Cloud
    • Utilizzare le capacità e i servizi offerti da SAP Business Technology Platform per costruire applicazioni di estensione più grandi
    • Utilizzare SAP Integration Suite
In tutto questo corso esploriamo queste best practice. Tuttavia, ci sono due punti importanti da notare. Il primo è che, poiché esistono due possibilità di deployment cloud che i clienti possono scegliere in base alle loro esigenze uniche, oltre a una terza opzione tradizionale on-premise, l’opzione specifica scelta determina esattamente quali opzioni possono (e non possono) essere utilizzate. Questo percorso formativo è principalmente orientato a SAP S/4HANA Cloud. Il termine SAP S/4HANA Cloud è un termine ombrello che si riferisce alle possibilità di deployment cloud, che sono SAP S/4HANA Cloud Public Edition e SAP S/4HANA Cloud Private Edition. Il termine SAP S/4HANA si riferisce all’opzione di deployment on-premise. Se devono essere fatte distinzioni tra SAP S/4HANA Cloud Public Edition e SAP S/4HANA Cloud Private Edition, il materiale lo indicherà esplicitamente. Salvo diversa indicazione, assumere che le funzionalità rilevanti per SAP S/4HANA Cloud Private Edition (ma non per SAP S/4HANA Cloud Public Edition) si applichino anche ai deployment on-premise.
Il secondo punto è che i clienti SAP ERP esistenti devono scegliere quale approccio di migrazione utilizzare quando passano a una delle possibili opzioni di deployment:
    • Nuova implementazione: viene provisionato un nuovo SAP S/4HANA Cloud o installato un nuovo sistema SAP S/4HANA
    • Conversione di sistema: un sistema SAP ERP esistente viene migrato a SAP S/4HANA Cloud Private Edition o a un sistema on-premise
    • Trasformazione del paesaggio: un ibrido dei primi due approcci
L’intersezione di queste due scelte influenza l’approccio specifico e i passaggi che un cliente sperimenta nel suo percorso di migrazione a SAP S/4HANA Cloud.

Classical Extensibility Approaches (Pre-Cloud)
Characteristics of the Classic Model
    • Designed for on-premise systems
    • Based on a clear contract between SAP and the customer
    • Customers were allowed to adapt standard software in a controlled but very permissive way
Example Scenario (Conceptual)
    • Standard application with Revenue and Cost
    • Customer requirement:
        ◦ Additional field Profit
        ◦ Profit calculated using a customer-specific factor
    • This factor did not exist in standard SAP tables

Classic Exit-Based Extensibility Stack
Data Layer Exits
    • Implemented via table appends
    • Allowed customers to:
        ◦ Add custom fields to SAP database tables
        ◦ Read and write those fields
    • Table append acted as a universal exit at data level
UI Layer Exits
    • Implemented via:
        ◦ Screen exits
        ◦ Menu exits
    • Used to:
        ◦ Display new fields
        ◦ Add user-triggered actions (for example profit calculation)
Code Layer Exits
    • Implemented via ABAP code exits
    • Used to:
        ◦ Read, calculate, update, and delete custom fields
    • Positioned between:
        ◦ Data layer
        ◦ UI layer

Governance of Classical Extensions
Controlled Development Process
    • Exits:
        ◦ Had to be activated
        ◦ Had to pass syntax and consistency checks
    • Development lifecycle:
        ◦ Development system
        ◦ Test system
        ◦ Production system
Freedom of Access (Very Important)
    • Extensions could:
        ◦ Read/write any SAP table
        ◦ Call any function module
        ◦ Use any SAP class and method
    • There were no technical restrictions

When No Exit Was Available
Customer Options
    1. Modify SAP objects directly
    2. Copy SAP objects and own them
Consequences
    • Modifications and copies:
        ◦ Were upgrade-critical
        ◦ Required extensive regression testing
    • Much more risky than exit-based extensions

Upgrade Impact of Classical Extensibility
Exit-Based Extensions
    • Known to SAP
    • Generally manageable during upgrades
    • Required testing, but effort was reasonable
Modifications and Copies
    • Highly problematic
    • Strong risk during patches and upgrades
    • High testing and maintenance cost

Why the Classical Model Worked for Decades
On-Premise Context
    • Systems hosted in customer-owned data centers
    • Each customer system was:
        ◦ Fully isolated
        ◦ Independent from others
    • Customer actions affected only their own system
Historical Scope
    • From SAP R/3
    • Through SAP Business Suite
    • Across service packs and enhancement packs

The Cloud Game Changer
Shift to SAP S/4HANA Cloud
    • All customers run on:
        ◦ The same core code line
    • Updates are:
        ◦ Applied simultaneously to all customers
    • Result:
        ◦ Classical extensibility model becomes unsustainable

Introducing the Clean Core Concept
What “Core” Means
The core of SAP S/4HANA Cloud includes:
    • Processes — End-to-end business execution
    • Data — Configuration, master, and transactional data
    • Integration — Connectivity with other solutions
    • Operations — Releases, jobs, authorizations, monitoring
    • Extensibility — Additional functionality beyond standard
What “Clean” Means
    • Each core aspect must be:
        ◦ Cloud-compliant
        ◦ Optimized
        ◦ Up-to-date
        ◦ Governed

Clean Core — Definition
Concept and Approach
    • Clean core is both:
        ◦ A concept
        ◦ An implementation approach
    • Goal:
        ◦ Modern, flexible, cloud-compliant SAP S/4HANA Cloud
    • Achieved by:
        ◦ Cloud-compliant integration
        ◦ Cloud-compliant extensibility
        ◦ High master data quality
        ◦ Strong process governance

Benefits of Clean Core
Customer Benefits
    • Upgrade stability
    • Fast innovation adoption
    • End-to-end security and system stability
    • Lower total cost of ownership (TCO)
    • Full traceability across the core
Partner Benefits
    • Cloud-ready, future-proof solutions
    • Fit-to-standard with modular innovation
    • Reduced complexity using SAP standard solutions

Clean Core Extensibility
Core Principle
    • Extensions are:
        ◦ Strictly separated from the SAP core
        ◦ Connected only via released, upgrade-stable interfaces
Key Exam Point
    • Extensions:
        ◦ Do NOT disappear
        ◦ Must NOT modify the core
        ◦ Must survive upgrades without risk

Clean Core Best Practices (Exam-Critical)
Extension Rules
    • Zero modifications policy
    • Remove redundant extensions and SAP object copies
    • Use only released APIs
    • Maximize key user (in-app) extensibility
    • Build larger extensions on SAP BTP
    • Use SAP Integration Suite

Deployment Options Context
SAP Deployment Models
    • SAP S/4HANA Cloud Public Edition
    • SAP S/4HANA Cloud Private Edition
    • SAP S/4HANA (on-premise)
Exam Rule

Transitioning to SAP S/4HANA Cloud
Diversi Approcci per la Transizione a SAP S/4HANA

Come menzionato nella lezione precedente, un cliente ha due decisioni importanti da prendere nel percorso verso SAP S/4HANA:
    1. Quale opzione di deployment di SAP S/4HANA utilizzare:
        ◦ SAP S/4HANA Cloud Public Edition
        ◦ SAP S/4HANA Cloud Private Edition
        ◦ SAP S/4HANA (on-premise)
    2. Se adottare una conversione di sistema (nota anche come Brownfield), una nuova implementazione (nota anche come Greenfield) o un approccio di trasformazione del paesaggio** (nota anche come Selective Data Transition).
Se il cliente decide di convertire il proprio sistema SAP ECC esistente, può scegliere SAP S/4HANA Cloud Private Edition o (se desidera mantenere il proprio landscape ERP on-premise) SAP S/4HANA. Lo stesso vale per l’approccio di trasformazione del paesaggio. Non esiste invece un’opzione di conversione di sistema o di trasformazione del paesaggio per SAP S/4HANA Cloud Public Edition; in questo caso, l’unica scelta possibile è una nuova implementazione. I clienti possono anche scegliere di adottare un approccio di nuova implementazione per SAP S/4HANA Cloud Private Edition o SAP S/4HANA se lo desiderano. Tutte le opzioni sono compatibili con un approccio clean core, ma possono influenzare il modo in cui viene eseguito e le sue varie sfaccettature.
Conversione di Sistema (Approccio Brownfield)
Con una conversione di sistema, il sistema SAP S/4HANA Cloud Private Edition o on-premise del cliente parte il più possibile vicino, sotto aspetti importanti, al loro sistema SAP ERP esistente. In pratica, il cliente costruisce il nuovo sistema SAP ERP utilizzando quello esistente come modello. Dopo la conversione, può iniziare il lavoro necessario basato sull’ambito del progetto. L’obiettivo di una conversione di sistema è ottenere un core pulito.
Nuova Implementazione (Approccio Greenfield)
Con una nuova implementazione, il sistema target (SAP S/4HANA Cloud Public Edition, SAP S/4HANA Cloud Private Edition, on-premise) di fatto non eredita alcun codice personalizzato dal sistema SAP ERP precedente. Il team di progetto non deve preoccuparsi di revert di modifiche o adattamento di estensioni. Inoltre, il sistema parte di default con un clean core. Ciò non significa che non saranno necessarie nuove estensioni basate sul modello di estendibilità di SAP S/4HANA Cloud (di cui si parlerà in una lezione successiva), ma il progetto di migrazione risulta più semplice in alcuni aspetti, grazie all’eliminazione del lavoro di conversione. In aggiunta, invece di un approccio “big bang” per il rilascio del nuovo sistema, può essere adottato un rollout graduale (ad esempio per codice azienda). Con una nuova implementazione, il sistema parte pulito di default, quindi l’obiettivo è mantenere il core pulito.
Trasformazione del Paesaggio (Landscape Transformation)
Per i clienti con un gran numero di sistemi ERP disparati (ad esempio, a seguito di frequenti fusioni e acquisizioni), una Selective Data Transition permette di consolidare configurazioni e dati provenienti da più sistemi ERP verso SAP S/4HANA Cloud Private Edition o un sistema on-premise.

Validating the Steps for System Conversions
Scenari di Conversione
Con una conversione di sistema, un cliente prende il proprio sistema SAP ERP esistente e lo converte in un sistema SAP S/4HANA on-premise. I passaggi specifici variano a seconda delle caratteristiche del sistema SAP ERP da convertire. In termini generali, possiamo distinguere tra i seguenti due scenari:
    1. SAP ERP in esecuzione su qualsiasi database
    2. SAP ERP in esecuzione su SAP HANA (v 1.0 o v 2.0)
SAP ERP in esecuzione su qualsiasi database
In questo scenario, l’attuale database non SAP HANA viene sostituito con un database SAP HANA v 2.0. Successivamente, avviene una conversione del modello di database, passando da SAP ERP a SAP S/4HANA. Infine, viene eseguito un upgrade del codice, installando il codice SAP S/4HANA che sostituisce il codice SAP ERP.
SAP ERP in esecuzione su SAP HANA (v 1.0 o v 2.0)
In questo scenario, poiché il sistema SAP ERP utilizza già un database SAP HANA, il primo passo è verificare se la versione è SAP HANA v 1.0. In tal caso, viene aggiornato a SAP HANA v 2.0. Successivamente, si procede con la conversione del modello dati e l’upgrade del codice, esattamente come nel primo scenario.
È importante notare che, in entrambi gli scenari, database, dati e software vengono convertiti nello stesso processo tecnico. Pertanto, è necessario un solo downtime del sistema.

Flussi di lavoro Clean Core

Una nuova implementazione ha un clean core di default. Tuttavia, anche in una conversione di sistema, è consigliato ottenere (e mantenere) il core il più pulito possibile. Come si fa questo? Utilizzando i flussi di lavoro raccomandati da SAP.

Collecting Usage Data for Custom Code
Valutazione del Codice Personalizzato

Nella prima lezione, abbiamo esaminato i diversi tipi di exit che tradizionalmente venivano implementati dai clienti per estendere le funzionalità delle applicazioni SAP standard. SAP S/4HANA utilizza applicazioni completamente ridefinite basate sull’esperienza UX di livello consumer (SAP Fiori, da trattare successivamente), oltre a nuovi modelli di dati e codice, quindi possiamo presumere che alcune estensioni non siano più necessarie. Ciò potrebbe dipendere dal fatto che lo scopo funzionale originale dell’estensione è ora coperto dalla funzionalità standard di SAP S/4HANA, oppure che i processi aziendali modificati rendono la funzionalità non più necessaria. In ogni caso, il codice contenuto in queste exit dovrebbe essere rimosso sistematicamente dal sistema. Ma come possiamo individuare e valutare questo codice? SAP raccomanda il seguente approccio:
    • Raccolta e aggregazione dei dati sull’utilizzo delle estensioni
    • Determinazione delle estensioni che possono essere rimosse tramite analisi del codice personalizzato
    • Preparazione della procedura di backup e ripristino
    • Verifica della funzionalità desiderata dell’app con l’estensione rimossa
    • Eliminazione dell’estensione durante la conversione del sistema


Raccolta e Aggregazione dei Dati sull’Utilizzo delle Estensioni

Sono stati creati due strumenti per aiutare i team di progetto nella raccolta dei dati sull’utilizzo delle estensioni. Può essere utilizzato uno qualsiasi dei due. Il primo è Usage and Procedure Logging (UPL) e il secondo è ABAP Call Monitor (codice transazione SCMON). Entrambi raccolgono informazioni relative all’esecuzione del codice ABAP in qualsiasi forma (metodi di classe, function module) e forniscono informazioni su quale codice ABAP viene eseguito e in quale contesto.
ABAP Call Monitor è lo strumento più recente dei due e offre un ulteriore livello di dettaglio fornendo informazioni anche sul chiamante del codice ABAP. Tuttavia, non è consigliato utilizzare entrambi gli strumenti contemporaneamente (per minimizzare eventuali problemi di performance del sistema); se UPL è già in uso e il cliente desidera continuare a utilizzarlo, va bene. È importante assicurarsi che il cliente utilizzi lo strumento scelto nel sistema produttivo, poiché l’effettivo utilizzo dell’estensione da parte degli utenti finali è il fattore determinante.
Entrambi gli strumenti sono in grado di integrare i dati raccolti con Solution Manager. Come regola generale, SAP raccomanda di eseguire lo strumento preferito per 6–18 mesi, includendo almeno una chiusura di fine anno.
Una volta raccolti i dati sull’utilizzo, il codice transazione SUSG può essere utilizzato per aggregare e gestire questi dati. Questo passaggio è importante poiché i dati raccolti tramite il codice transazione SCMON vengono eliminati dopo un breve periodo di tempo.


Determinazione delle Estensioni che Possono Essere Rimosse tramite Analisi del Codice Personalizzato

Qui, il team di progetto ha due opzioni per eseguire l’analisi del codice personalizzato. La prima è utilizzare l’app SAP Fiori Custom Code Migration. L’app può essere trovata su un sistema sandbox SAP S/4HANA appena convertito e utilizzato per i test (approfondiremo questo argomento a breve). Se un sistema sandbox SAP S/4HANA non è ancora disponibile, l’app può essere trovata e utilizzata tramite la SAP Business Technology Platform, ambiente ABAP, ed eseguita contro un sistema SAP ERP tramite RFC e Cloud Connector.
La seconda opzione è utilizzare l’ABAP Test Cockpit, disponibile come parte degli ABAP Development Tools per Eclipse.
Un vantaggio dell’app SAP Fiori è che, basandosi sulle statistiche di utilizzo raccolte da Usage and Procedure Logging (UPL) e ABAP Call Monitor, può identificare le estensioni non utilizzate. Queste estensioni non utilizzate possono poi essere rimosse durante la conversione del sistema (vedi la sezione Eliminazione dell’Estensione Durante la Conversione del Sistema).


Preparazione della Procedura di Backup e Ripristino

È comprensibile che possano sorgere preoccupazioni legittime riguardo alla cancellazione del codice non utilizzato, soprattutto se esiste la possibilità che possa essere necessario nuovamente in futuro. Per questo motivo, il team di progetto può progettare e adottare una procedura di backup e ripristino. Esistono diversi approcci che possono essere considerati. Uno potrebbe essere un sistema ABAP separato appositamente previsto per il backup. Un altro potrebbe essere un sistema di backup fornito da un prodotto di terze parti.
Pur essendo entrambe opzioni adottabili, un fattore da considerare è il costo di mantenimento (o di acquisto) di un sistema dedicato esclusivamente al backup. Per affrontare questa preoccupazione, SAP ha creato l’opzione “Git-enabled Change and Transport System” (gCTS) da considerare. Essa utilizza un repository Git esterno per memorizzare il codice non utilizzato. Per ulteriori informazioni sul backup del codice personalizzato con gCTS, consultare “How to backup custom code with gCTS”.
Un punto importante da ricordare è che, indipendentemente dall’approccio di backup adottato, se è necessario un ripristino, la procedura di ripristino deve includere controlli ABAP sul codice (a tale scopo deve essere utilizzato l’ATC) e test del codice. Una volta conclusi questi controlli e test e verificato che non vi siano problemi, l’estensione ripristinata può essere trasportata in produzione.


Verifica della Funzionalità Desiderata dell’App con l’Estensione Rimossa

Si tratta di un test normale eseguito dal team di quality assurance per assicurarsi che non vi siano problemi tecnici con l’estensione rimossa.

Adapting Custom Code
Adattamento del Codice Personalizzato

Questo flusso di lavoro nasce perché esistono differenze significative sia nel modello dati sia nella base di codice tra SAP ERP e SAP S/4HANA. Le estensioni ritenute necessarie e quindi mantenute (o le estensioni che vengono eliminate ma successivamente devono essere ripristinate) devono sottoporsi a un processo di adattamento. Questo processo può assumere una delle due forme seguenti:
    • Adattamento automatico del codice personalizzato
    • Adattamento manuale del codice personalizzato
Prima di differenziare tra i due approcci, c’è un argomento preliminare da esplorare. Nella maggior parte dei casi, il team di implementazione del progetto crea una copia del sistema di produzione SAP ERP in un sistema sandbox speciale. Questa sandbox viene quindi utilizzata per testare la conversione prima di eseguirla sul sistema di produzione effettivo. Questo è sensato perché il sistema di test dovrebbe replicare la produzione il più possibile. È anche sensato eseguire gli adattamenti del codice personalizzato in questo sistema sandbox, e SAP generalmente raccomanda che i team di progetto lo facciano.
Tuttavia, ciò può portare a una complicazione. Mentre il progetto di migrazione verso il nuovo SAP S/4HANA è in corso, il sistema SAP ERP esistente necessita ancora delle normali attività di manutenzione e supporto. Al momento in cui il team di progetto è pronto a eseguire la conversione del sistema in produzione, potrebbero esserci differenze significative tra il sistema di produzione e la sandbox usata per i test.
Esistono tre possibili soluzioni per risolvere questo problema:
    1. Blocco dello sviluppo (Development freeze)
Una soluzione consiste nel bloccare semplicemente lo sviluppo nel sistema SAP ERP (che diventerà legacy). Sebbene teoricamente questa opzione possa funzionare, implica che le normali attività di manutenzione, supporto e, soprattutto, innovazione, vengano interrotte per un periodo indefinito. È molto probabile che il business si opponga a questa soluzione.
    2. Doppio lavoro (Double work)
Un’altra soluzione sarebbe rifare tutto il lavoro di adattamento del codice personalizzato eseguito nel sistema sandbox sul nuovo sistema SAP S/4HANA convertito. Anche questa opzione, teoricamente, funzionerebbe, ma a seconda della quantità di lavoro di adattamento da rifare, potrebbe essere estremamente laboriosa.
    3. Retrofit con Solution Manager (Solution Manager retrofit)
La soluzione preferita è utilizzare la funzionalità retrofit con Solution Manager (versione 7.2 Ehp 8 o superiore).
Adattamento Automatico del Codice Personalizzato
Come menzionato in precedenza, i team di progetto hanno tre opzioni per l’analisi del codice personalizzato:
    • L’app SAP Fiori Custom Code Migration (su SAP S/4HANA o la stessa app su SAP Business Technology Platform, ambiente ABAP)
    • L’ABAP Test Cockpit, disponibile come parte degli ABAP Development Tools per Eclipse
L’app SAP Fiori Custom Code Migration è integrata con l’ABAP Test Cockpit dietro le quinte, quindi tutte e tre le opzioni possono utilizzare la funzionalità Quick Fix del cockpit per correggere automaticamente (e, se necessario, attivare) il codice ABAP in conformità con le modifiche di SAP S/4HANA.
Adattamento Manuale del Codice Personalizzato
Il codice che non può essere adattato automaticamente deve essere adattato manualmente. Il processo varia da progetto a progetto e da organizzazione a organizzazione, in base a diversi fattori. Il seguente processo suggerito può essere utilizzato come punto di partenza per l’analisi:
    1. Utilizzare l’app SAP Fiori SAP Readiness Check Tool per ottenere un elenco delle SAP Notes rilevanti che descrivono l’impatto sul codice personalizzato.
    2. Dopo aver studiato le SAP Notes, differenziare tra quelle che specificano correzioni tecniche del codice e quelle che richiedono conoscenze applicative più specializzate. Utilizzare questa differenziazione per organizzare i team di adattamento di conseguenza.
    3. Inoltre, se i singoli sviluppatori possono specializzarsi in determinati tipi di modifiche del codice (basandosi sulle SAP Notes rilevanti), questo può rendere il processo di adattamento manuale più efficiente. Tuttavia, ciò potrebbe non essere sempre possibile.
    4. Determinare un tempo esatto per completare tutte le modifiche manuali richieste è irrealistico (e molto probabilmente errato). È consigliato comunicare una stima di intervallo temporale agli stakeholder del progetto di migrazione.

Evaluating SAP Fiori
L'importanza di un'esperienza utente di livello consumer

Non importa quanto innovativa sia un'applicazione software, è l'adozione riuscita da parte degli utenti finali a determinare in ultima analisi il suo successo o fallimento, e nulla è più correlato a questa adozione riuscita dell'esperienza utente (UX) che l'applicazione offre.
Perché la UX è così importante? Oggi, a differenza del passato, gli utenti finali si aspettano che le applicazioni aziendali abbiano lo stesso aspetto visivo e la stessa sensazione delle applicazioni che utilizzano ogni giorno su telefoni, tablet e siti Web.
Come discusso nella lezione Introducing the Clean Core Approach, le esigenze degli utenti finali, pur essendo importanti, devono essere bilanciate con le esigenze dell'azienda e del reparto IT. Fortunatamente, in questo caso, questo bilanciamento risulta in una situazione vantaggiosa per tutti. Oltre a utenti finali soddisfatti, una UX ben progettata riduce i costi di formazione, poiché gli utenti finali richiedono meno tempo per apprendere l'applicazione. Le applicazioni ben progettate presentano anche meno errori, il che porta il reparto IT a dedicare meno tempo alla gestione dei ticket di supporto, per non parlare di una maggiore produttività da parte degli utenti finali. Infine, meno errori portano a meno reclami dei clienti, il che si traduce in un Net Provider Score più elevato – qualcosa che tutte le aziende apprezzano.
Cos’è la UX?
Ora che abbiamo capito perché la UX è così importante, passiamo a esaminare cosa sia esattamente la UX. Esistono alcune variazioni della definizione, il che è comprensibile e non necessariamente problematico. Un buon punto di partenza per una definizione è l'Organizzazione Internazionale per la Standardizzazione (ISO). La ISO 9241 definisce l'esperienza utente come le "percezioni e risposte di un utente che risultano dall'uso e/o dall'uso previsto di un sistema, prodotto o servizio". Le percezioni menzionate nella definizione ISO sono influenzate dall'applicazione utilizzata insieme all'uso in questione e al contesto in cui l'applicazione viene utilizzata.
Questa definizione è un buon punto di partenza per la UX di livello consumer di SAP – uno dei pilastri della strategia di prodotto di SAP S/4HANA Cloud. Per SAP, la UX di livello consumer significa applicazioni aziendali che hanno l'aspetto e la sensazione "consumer" che gli utenti finali desiderano. La UX di livello consumer è incarnata in modo più chiaro in SAP Fiori. SAP Fiori è un sistema di design che comprende tutti gli aspetti necessari per uno sviluppo UX efficace. Questi aspetti includono gli elementi visivi che compongono un'applicazione, i concetti di navigazione, le opzioni di provisioning dell'applicazione e altro ancora.
Oltre alla strategia di prodotto, SAP Fiori è anche una parte importante dell'approccio clean core. Ricorda che nella lezione Introducing the Clean Core Approach abbiamo menzionato che una delle componenti dell'approccio clean core è l'uso di interfacce ben definite e stabili agli aggiornamenti. I dati di SAP S/4HANA Cloud vengono forniti a un'app SAP Fiori tramite interfacce, specificamente API remote – l'esplorazione delle quali vedremo in una lezione successiva.

Vantaggi di SAP Fiori

Coerenza delle app SAP Fiori e SAP Fiori Elements
Sia le app SAP Fiori sia le app SAP Fiori Elements sono costruite utilizzando SAPUI5. SAPUI5, a sua volta, si basa su tecnologie Web standardizzate. SAPUI5 utilizza HTML5 insieme a CSS3 e JavaScript. Sfrutta anche due librerie ben note e popolari: LESS e jQuery. SAPUI5 dispone di quasi 200 controlli standard che uno sviluppatore può utilizzare per costruire le interfacce utente. Questi controlli hanno lo stesso aspetto e comportamento indipendentemente dall'applicazione in cui vengono utilizzati. Pertanto, sia che si tratti dell'app Cash Flow Analyzer utilizzata dal reparto finanza, sia dell'app Count Physical Inventory utilizzata da un addetto al magazzino, i tipi di elementi sono gli stessi.
SAP Business Application Studio
SAP Business Application Studio è un servizio disponibile su SAP Business Technology Platform (BTP). SAP Business Application Studio è un ambiente di sviluppo moderno e integrato che può essere utilizzato per creare app SAP Fiori. Utilizzando un insieme di strumenti e wizard integrati, la struttura del progetto, insieme ai file contenenti il codice, può essere generata automaticamente in pochi clic. Questo comporta una riduzione straordinaria del tempo di sviluppo rispetto alla creazione di tutti i componenti del progetto da zero.
SAP Fiori Elements e Fiori Tools
SAP Fiori Elements può ridurre ulteriormente i tempi di sviluppo. Quando un team di progetto progetta un'app SAP Fiori, una delle decisioni da prendere è se sviluppare l'app in modalità freestyle o con SAP Fiori Elements. Sebbene SAP Business Application Studio generi in entrambi i casi tutti i componenti necessari del progetto, SAP Fiori Elements consente di scalare lo sviluppo di SAP Fiori offrendo un approccio basato su template e metadata per la creazione delle app. Ciò riduce la quantità di sviluppo front-end necessario (rispetto all'approccio freestyle) per creare l'applicazione, permettendo di concentrarsi sulla logica aziendale e sui servizi back-end richiesti.
Le app SAP Fiori Elements sono automaticamente di livello enterprise. Il framework garantisce codice UI di alta qualità, stabile e ottimizzato. Fornisce anche molte funzionalità pronte all'uso che ci si aspetta nello spazio enterprise, ma che normalmente sarebbero piuttosto costose da implementare, come accessibilità, gestione delle varianti o modalità di modifica.
SAP Fiori Elements categorizza le applicazioni per scopo (ad esempio, Analytics, Worklist) in uno dei diversi floorplan. Il floorplan è scelto dallo sviluppatore in SAP Business Application Studio durante lo sviluppo dell'applicazione. Tuttavia, a differenza della generazione UI5 freestyle, i file HTML5, CSS e JavaScript non vengono generati. Viene invece creato un insieme di file contenenti annotazioni basate su XML. Queste annotazioni vengono valutate a runtime dall'ambiente SAPUI5 quando l'utente finale avvia l'applicazione, e l'interfaccia utente viene renderizzata dinamicamente.
Alcuni dei floorplan disponibili sono:
    • Analytical List
    • Page
    • Initial Page
    • List Report
    • Object Page
    • Overview Page
    • Wizard
    • Worklist
Se il team di progetto ha bisogno di estendere un'app SAP Fiori Elements per il proprio caso d'uso, ha sempre la possibilità di aggiungere codice personalizzato all'app. Nel Flexible Programming Model, uno sviluppatore farebbe ciò in Freestyle UI5 sfruttando il framework JavaScript e la libreria UI5 UI.
Oltre al Flexible Programming Model, lo sviluppatore può utilizzare un approccio aggiuntivo per migliorare ulteriormente l'applicazione con le funzionalità richieste. Un'applicazione SAP Fiori Elements può essere “legata” a un servizio OData implementato sulla piattaforma ABAP (specificamente, una vista Core Data Services – CDS). Le annotazioni possono essere inserite nella vista CDS e saranno valutate a runtime dall'ambiente UI5. Insieme alla possibilità di inserire annotazioni nel progetto SAP Business Application Studio, queste due opzioni offrono allo sviluppatore flessibilità nella progettazione di un'applicazione. Le annotazioni con uno scopo più globale possono essere inserite a livello ABAP (evitando allo sviluppatore di doverle copiare più volte in app diverse). Annotazioni più specifiche (che possono variare da app a app, in base ai requisiti degli utenti finali) possono essere inserite in ciascuna applicazione individuale. I vantaggi potenziali di questo collegamento tra il livello ABAP e il livello UX diventano più evidenti in una lezione successiva, quando esploreremo i diversi tipi di estensioni possibili nel modello di estensibilità di SAP S/4HANA Cloud.
Processo di test più semplice
SAP Business Application Studio offre una vasta gamma di strumenti di test per aiutare gli sviluppatori. Il codice XML, JavaScript e JSON beneficia di inserimento e completamento automatico del codice. Tutti e tre i linguaggi vengono controllati sintatticamente con strumenti integrati. Gli sviluppatori possono avviare direttamente dall'ambiente di sviluppo integrato le app SAP Fiori su cui stanno lavorando.
Terminologia di sviluppo standardizzata
SAP Fiori si basa sulla popolare filosofia di sviluppo “a livelli”. Un livello dati fornisce la persistenza. Un livello servizio fornisce un’implementazione delle operazioni create, read, update e delete (CRUD). Il livello visivo è implementato secondo il popolare pattern Model View Controller (MVC), familiare alla maggior parte degli sviluppatori e facile da apprendere per chi non lo conosce. Ogni elemento del pattern MVC ha un insieme definito di oggetti di sviluppo con caratteristiche specifiche. Grazie a questa standardizzazione, la comunicazione tra i membri del team di progetto è più semplice, lo sviluppo delle app è più efficiente e la manutenzione delle app più lineare.

Basato sul ruolo
Le applicazioni SAP Fiori vengono assegnate agli utenti finali tramite il concetto di ruolo, gestito tramite la transazione PFCG. Le app SAP Fiori vengono assegnate a due tipi di artefatti: Cataloghi e Gruppi. Adattabile
Una delle richieste principali degli utenti finali oggi è la possibilità di utilizzare il dispositivo di loro scelta per svolgere il lavoro. Gli utenti finali non solo utilizzano telefoni, tablet e desktop, ma si aspettano anche di poter iniziare un processo su un dispositivo e terminarlo su un altro dispositivo diverso. SAP Fiori ha l’adattabilità integrata nel suo nucleo. Un’applicazione si adatta in base al tipo di dispositivo su cui viene utilizzata. Le capacità di bozza (draft) presenti a livello ABAP permettono agli utenti finali di interrompere temporaneamente l’esecuzione dell’applicazione e completarla in un momento successivo.

Nel mondo SAP Fiori, queste applicazioni vengono scomposte in piccole applicazioni modulari, basate sul principio di “uno” – una singola applicazione per uno scopo specifico.
Coerente
Indipendentemente dall’app SAP Fiori che un utente finale sta utilizzando e indipendentemente dallo scopo per cui la utilizza, l’interazione e l’esperienza visiva sono coerenti in tutta l’azienda.
Piacevole

L’emergere del Builder

Nella lezione Introducing SAP S/4HANA Cloud abbiamo appreso che uno dei vantaggi del cloud computing è la rapida erogazione dell’innovazione tramite aggiornamenti software frequenti e regolari. Inoltre, nella lezione precedente, abbiamo discusso di come una strategia UX di livello consumer ben progettata e eseguita porti all’adozione riuscita del software, e abbiamo visto come le app SAP Fiori offrano ai clienti un percorso per garantire questa adozione. Esiste un altro percorso altrettanto importante e disponibile per i clienti da utilizzare per l’adozione, che esploriamo in questa sezione.
Le rapide innovazioni derivanti dal cloud computing portano inevitabilmente a cambiamenti altrettanto rapidi nei requisiti aziendali. Requisiti aziendali in rapido cambiamento significano applicazioni software che devono essere create e modificate rapidamente. Sebbene questo non sia necessariamente negativo, esiste un reale vincolo di risorse: la capacità IT. Mentre la capacità fisica, come potenza di calcolo, memoria e simili, può essere scalata per soddisfare le esigenze di risorse in cambiamento, le persone (in particolare gli sviluppatori) non scalano altrettanto facilmente. Questo ha portato a una carenza di sviluppatori in molti, se non nella maggior parte, dei reparti IT delle organizzazioni.
Questa tensione tra la necessità di sviluppare un numero maggiore di app e la rapidità con cui devono essere sviluppate ha reso necessario un cambiamento di mentalità su chi fa sviluppo. Entra in scena il Citizen Developer, che SAP definisce Builder. Un builder è qualcuno che crea app (spesso per una specifica LoB) utilizzando strumenti specializzati preapprovati dal reparto IT e messi a disposizione per lo sviluppo. Questo offre alle aziende un’opzione aggiuntiva per lo sviluppo di applicazioni, oltre all’acquisto di app preconfezionate o alla creazione di app da zero (entrambe richiedono sviluppatori qualificati).
Gli sviluppatori necessitano ancora di strumenti specializzati per i loro scopi – strumenti basati su un linguaggio e modello di programmazione specifici, con debugger integrati e capacità avanzate di test. I builder non hanno bisogno dello stesso tipo di strumenti. Gli strumenti preapprovati dal reparto IT per l’uso dei builder sono spesso definiti strumenti low-code/no-code, abbreviati LCNC.
Low-code è un metodo per progettare e sviluppare applicazioni utilizzando strumenti grafici intuitivi e funzionalità incorporate che riducono la necessità di scrittura tradizionale – o pro-code.
No-code è un metodo che beneficia di un’esperienza utente simile al low-code, ma va oltre permettendo agli utenti aziendali non tecnici di sviluppare applicazioni senza dover scrivere una singola riga di codice.

Evaluating Cloud Native and REST
Principi Cloud Native

In questa unità, approfondiamo il modello di sviluppo ABAP Cloud (ABAP Cloud), il modello in cui le applicazioni cloud native possono essere sia create che eseguite su ABAP. Ma poiché ABAP Cloud è in parte ispirato dall’emergere del cloud computing e del paradigma cloud native, è opportuno una breve discussione su entrambi gli argomenti.
Come discusso nel corso S4CP01: Exploring SAP Cloud ERP, nell’attuale contesto aziendale, le aziende devono adattare rapidamente i processi aziendali per rispondere alle condizioni di mercato in cambiamento e alle mutevoli richieste dei clienti. Questa necessità di adattamento richiede applicazioni scalabili, robuste e, cosa importante, flessibili. Gli ambienti di cloud computing sono un modo per affrontare questa esigenza. L’altro è il cloud native.
Cloud Computing
Il cloud computing è comunque informatica, ma è progettato in modo diverso rispetto alla tipica infrastruttura di data center on-premise a cui il personale IT era tradizionalmente abituato. Con l’infrastruttura on-premise (spesso chiamata data center on-premise), il cliente è responsabile dell’installazione e della manutenzione degli elementi fisici, come server e apparecchiature di rete. Con il cloud computing, questi componenti infrastrutturali sono forniti da un provider cloud esterno.
In generale, i seguenti componenti sono forniti dal provider cloud:
    • Rete
    • Server (fornendo capacità di calcolo e memoria)
    • Storage
    • Sistemi operativi e virtualizzazione
La configurazione iniziale di questi componenti, così come le operazioni, la manutenzione e gli aggiornamenti continui, sono gestiti dal provider cloud.
Principi del Cloud Computing
Questi componenti sono messi a disposizione del cliente seguendo i seguenti principi:
Elasticità
La maggior parte delle organizzazioni sperimenta picchi e cali nell’uso delle risorse. Ad esempio, l’elaborazione delle buste paga può avvenire due volte al mese e durante quei periodi è necessaria capacità aggiuntiva di rete e server. I provider cloud offrono tipicamente una funzione di elasticità per i clienti come parte della loro offerta. In questo modo, man mano che sono necessarie più risorse, queste possono essere allocate e sia le prestazioni individuali sia quelle complessive dell’applicazione possono essere mantenute ai livelli desiderati.
Prezzi
I componenti del cloud computing sono offerti ai clienti secondo un piano di prezzo e consumo concordato. Questo può variare da provider a provider. SAP, ad esempio, offre vari runtime e servizi come parte della sua offerta Platform as a Service (PaaS) SAP BTP, non solo con un piano basato su abbonamento, ma anche con due diversi tipi di piani di acquisto basati sul consumo.
Disponibilità
Tornando all’esempio della busta paga menzionato in precedenza, la disponibilità delle risorse di cloud computing è semi-mensile (assumendo che la busta paga venga eseguita due volte al mese). Per altri tipi di processi aziendali (ad esempio i processi di gestione della supply chain), la disponibilità varia a seconda del tipo di processo in questione e di come l’azienda sceglie di operare. Per le organizzazioni più grandi, in particolare, è giusto dire che 24 ore al giorno, sette giorni su sette, almeno un processo ha bisogno di risorse per poter essere eseguito. È qui che entra in gioco la disponibilità. Come parte della loro offerta, i provider cloud comunicano in modo trasparente ai clienti la disponibilità prevista dei loro componenti. Ancora una volta, pur non essendo tecnicamente obbligatorio, quasi tutti i provider offrono un’opzione di disponibilità 24x7, dando ai clienti la massima flessibilità se determinate operazioni devono essere eseguite in modo continuo o a intervalli imprevedibili.
Service Level Agreement (SLA)
Strettamente legato alla disponibilità è il service level agreement (SLA). Mentre la disponibilità è solitamente espressa come un numero (24x7), l’SLA aggiunge una dimensione temporale (cioè 24x7 per il 99,99% del mese). Utilizzando questo esempio, se un mese ha 30 giorni, ciò si tradurrebbe in 43.200 minuti (30 giorni per 24 ore al giorno per 60 minuti all’ora). Con un SLA del 99,99%, il sistema non sarebbe disponibile (nel corso di quel mese) per circa quattro minuti e mezzo (0,0001 volte 43.200).
C’è una differenza?
Sebbene inizialmente possa essere tentante pensare: "A parte il provider, sembra che non ci sia differenza pratica tra cloud computing e un data center fornito dal cliente", questo non dovrebbe essere il caso. Le conseguenze di avere un’infrastruttura informatica fornita da un provider cloud significano che le applicazioni software dovrebbero essere progettate per essere indipendenti dall’infrastruttura. Dovrebbero funzionare allo stesso modo indipendentemente dal server specifico, dal sistema operativo o dal sistema di storage fornito dal provider cloud. È del tutto concepibile che un provider cloud possa cambiare frequentemente la propria infrastruttura. Inoltre, un cliente potrebbe decidere di cambiare provider cloud (cioè, un provider diverso offre prestazioni SLA superiori). Inoltre, la necessità di adattare rapidamente le applicazioni significa che non dovrebbe essere necessario testare un’applicazione su diversi tipi di infrastruttura per garantirne la compatibilità, per non parlare del tempo e del costo di sviluppare diverse versioni di un’applicazione solo per poterla eseguire su diversi tipi di infrastruttura, il che, ancora una volta, è inaccettabile. Dal punto di vista dello sviluppatore (e in ultima analisi dell’utente finale), i componenti infrastrutturali utilizzati nel cloud computing rappresentano un’astrazione.
Per garantire questa astrazione, è necessario un ripensamento completo, dall’alto al basso, dei modelli di programmazione, degli strumenti e delle tecnologie utilizzate per lo sviluppo e la manutenzione delle applicazioni nel cloud computing. Il cloud native è emerso come risultato di questo ripensamento.
Che cos’è il Cloud Native?

Cloud native è, prima di tutto, un approccio – un approccio allo sviluppo, al deploy e alla manutenzione delle applicazioni software in un ambiente di cloud computing, che permette un’adattabilità e una flessibilità rapide delle applicazioni. Sebbene la definizione specifica di cloud native vari da fonte a fonte, a seconda di quale definizione venga utilizzata, ci sono alcuni componenti su cui tutte le definizioni generalmente concordano e che diventano molto importanti per comprendere il modello di sviluppo ABAP Cloud:
    • Indipendenza dall’infrastruttura
    • Microservizi
    • Application Programming Interfaces (API)
Indipendenza dall’infrastruttura
Come menzionato in precedenza, il provider cloud fornisce i componenti infrastrutturali, che costituiscono un ambiente di cloud computing (cioè rete, server (che forniscono capacità di calcolo e memoria), storage, sistemi operativi e virtualizzazione). Diversi provider cloud forniscono queste risorse usando tecniche, configurazioni, marche e così via differenti. Un’applicazione cloud native funziona allo stesso modo indipendentemente da queste differenze e dal provider cloud.
Microservizi
Molti modelli di programmazione cloud native seguono un approccio a tre livelli per lo sviluppo delle applicazioni. Il primo è il livello utente (talvolta chiamato livello di consumo), che è responsabile della resa visiva dell’interfaccia utente con cui gli utenti finali interagiscono. Il secondo è il livello dati, dove i dati di cui l’applicazione ha bisogno sono memorizzati permanentemente in una qualche fonte dati (normalmente un database). Tra questi due livelli c’è il livello dei servizi. Il livello dei servizi risponde alle richieste generate dal livello utente da una parte e, nel farlo, esegue operazioni sui dati nella sua fonte dati a livello del livello dati. Queste operazioni sono comunemente categorizzate in quattro tipi, spesso chiamati operazioni CRUD:
    • Create (Creare)
    • Read (Leggere)
    • Update (Aggiornare)
    • Delete (Cancellare)
Sebbene non sia obbligatorio, questi livelli sono spesso progettati per essere eseguiti in posizioni e in tipi di ambienti runtime differenti. Alcune di queste posizioni e ambienti possono essere basati sul cloud, altri on-premise. Questo approccio ibrido non è raro ed è utilizzato da molti clienti. La progettazione a microservizi significa che ogni livello è implementato come un proprio componente autonomo. In quanto tale, può essere mantenuto e adattato separatamente dagli altri livelli, pur potendo comunicare e coordinarsi con essi nel contesto di un’applicazione completa.
Application Programming Interfaces (API)
La comunicazione e il coordinamento menzionati nella sezione precedente vengono effettuati tramite l’uso delle API. Un’API è una tecnica mediante la quale due componenti software possono comunicare tra loro e scambiare o manipolare informazioni utilizzando definizioni e rappresentazioni dei dati concordate (queste sono spesso chiamate protocollo). Ad esempio, un’app che molte persone hanno usato è un’app bancaria che permette all’utente di eseguire varie funzioni, come controllare il saldo del proprio conto o iniziare un bonifico per pagare una bolletta. L’app può essere accessibile liberamente tramite Internet usando il sito web della banca, oppure installata su un telefono mobile. In entrambi i casi, il design dell’app prevede che dietro le quinte venga utilizzata una o più API per eseguire le varie funzioni bancarie richieste dall’utente finale dell’app. Ogni API è progettata per eseguire un compito di cui un’app potrebbe avere bisogno ed è tipicamente disponibile “su richiesta” per essere utilizzata. L’uso è generalmente basato su qualche forma di processo “call and response” (cioè, l’app chiama l’API e l’API risponde in qualche modo).
La banca in questo scenario fornisce le API (poiché ha la governance legale dei conti bancari) e, a sua discrezione, può metterle a disposizione per l’uso da parte di terzi (sviluppatori che progettano prodotti dove desiderano aggiungere funzionalità bancarie, ad esempio), così come utilizzarle direttamente nello sviluppo della propria app. Le API esistono da molti decenni e precedono il cloud computing. Tuttavia, il concetto di API si è evoluto per comprendere le esigenze del cloud computing e dello sviluppo a microservizi. Uno dei modi in cui questa evoluzione si è manifestata è nell’adozione di una delle architetture API più comuni oggi in uso: Representational State Transfer (REST).
Principi architetturali REST

Continuando con l’esempio dell’app bancaria che utilizza un’API, ad esempio per controllare il saldo del conto, possiamo apprendere una terminologia REST importante. In REST, c’è un termine speciale utilizzato per indicare le informazioni di cui un’applicazione potrebbe avere bisogno, ossia una “risorsa” (in questo caso, il conto bancario). Questa risorsa ha uno “stato” (un conto bancario ha sempre un saldo) e questo stato può cambiare (i saldi bancari aumentano o diminuiscono) ma in ogni momento, questo stato esiste. In terminologia REST, questo stato è comunemente chiamato “rappresentazione della risorsa”. Questo stato può essere richiesto (“Dimmi il mio saldo, per favore”) e può anche essere modificato (“Ecco un assegno da depositare sul mio conto; dimmi il mio saldo aggiornato”). Infine, tutta questa comunicazione tra l’app e l’API avviene su Internet, il che significa che lo stato deve essere “trasferito” avanti e indietro. Ed ecco spiegato: [Resource] “Representational” “State” “Transfer”.
Riepilogo Representational State Transfer
    • Un insieme di vincoli architetturali
    • Un insieme di regole che gli sviluppatori seguono quando creano la loro API
    • Un’architettura client-server composta da client, server e risorse, con le richieste gestite tramite HTTP
    • Comunicazione client-server stateless, cioè senza memorizzazione delle informazioni del client tra le richieste, e ogni richiesta è separata e indipendente
Principi architetturali REST
Le API REST sono sviluppate basandosi su un modello architetturale ancorato ai seguenti principi:
Uniform Resource Interface
Una risorsa (un conto bancario, nel nostro caso) è identificata in modo univoco tramite un unico meccanismo di indirizzamento. Ad esempio, http://www.somebankserver.com/Account.
Client-Server
Coerentemente con un approccio di progettazione a microservizi, il client (in questo caso, l’app) e il server (dove risiede l’API) sono livelli separati che comunicano tra loro tramite Internet.
Stateless
Una procedura di trasferimento stateless significa che il client invia una richiesta (un’app richiede il controllo del saldo del conto) e quando l’API ospitata sul server restituisce il saldo come risposta, l’API non memorizza alcuna informazione relativa a quella richiesta. Se, un attimo dopo, l’app richiede nuovamente il saldo dello stesso conto, l’API la gestirà come una richiesta completamente nuova, senza utilizzare nulla della richiesta precedente (neanche esserne consapevole).
L’applicazione più popolare su Internet è il World Wide Web (Web), che utilizza il protocollo HTTP per trasferire informazioni avanti e indietro tra vari client e server. Poiché il protocollo HTTP è stateless, esso funge da protocollo utilizzato da REST per il trasferimento.
Cacheable
Per migliorare scalabilità e prestazioni, il caching può essere implementato per un’API REST. Alcuni dati possono essere memorizzati in modo da consentire un accesso ad alta velocità e rispondere alle richieste più rapidamente. Ad esempio, i saldi dei conti bancari possono essere memorizzati nella cache invece di essere recuperati da un database remoto.
Layered System
Sistemi intermedi sono permessi (ad esempio per bilanciamento del carico o autenticazione). Il client potrebbe non essere consapevole di questi sistemi intermedi e la comunicazione client-server non sarà influenzata o compromessa negativamente.
Code on Demand
I server possono trasferire codice eseguibile (ad esempio JavaScript) al client per estenderne le capacità. Questo è l’unico principio opzionale.
REST e CRUD
Come discusso in precedenza, il livello servizi si trova tra il livello utente e il livello dati, e media la comunicazione tra i due. Le API REST risiedono al livello servizi e operano come server nelle comunicazioni client-server (con il livello utente che agisce come client). Poiché REST utilizza HTTP come protocollo di trasferimento e comunicazione sottostante, tutte le richieste API REST sono anche richieste HTTP. I client utilizzano quattro metodi HTTP di base per interagire con un’API REST, come segue:
    • HTTP POST per eseguire un’operazione di creazione su una risorsa
    • HTTP GET per recuperare una specifica risorsa
    • HTTP PUT per eseguire un’operazione di aggiornamento su una risorsa
    • HTTP DELETE per eliminare una risorsa
I client inviano richieste HTTP basate su questi metodi all’API REST, che a sua volta esegue le operazioni richieste sulle risorse applicabili e restituisce risposte HTTP ai client.
Come accennato in precedenza, REST è diventata una delle architetture API più popolari nell’approccio cloud native. Le applicazioni cloud native che utilizzano un design a microservizi insieme alle API REST sono ben adatte alle esigenze dei consumatori moderni per app che girano su dispositivi mobili e desktop, con interfacce utente moderne ed eleganti. SAP e ABAP in particolare non sono immuni da queste aspettative. Di conseguenza, è emersa la necessità che ABAP evolvesse per abbracciare il cloud computing e i concetti cloud native.

Caratteristiche del Modello di Sviluppo ABAP Cloud

Da ABAP Classic al Modello di Sviluppo ABAP Cloud

Nel corso finora, abbiamo più volte sottolineato quanto sia diventato fondamentale che le aziende dispongano di applicazioni flessibili, facilmente adattabili alle mutevoli esigenze dei clienti. SAP S/4HANA Cloud è il prodotto che risponde a questa necessità, e il principio di clean core extensibility è quello che abilita questa flessibilità. Nella lezione precedente, abbiamo visto che il cloud computing ha assunto un ruolo centrale diventando una piattaforma per lo sviluppo e l’operatività delle applicazioni. In quella lezione, abbiamo anche visto come il cloud computing abbia portato all’evoluzione di un approccio diverso nello sviluppo e nella manutenzione delle applicazioni, ovvero il cloud native. Infine, in quella lezione, abbiamo visto che un aspetto particolare del cloud native, le API REST, è centrale per il suo successo.
Evoluzione, non rivoluzione
L’emergere del cloud computing, del cloud native e delle REST API, insieme al principio di clean core extensibility, ha reso necessaria un’evoluzione del linguaggio ABAP e dei modelli di sviluppo ABAP utilizzati dagli sviluppatori nel corso degli anni. Fortunatamente, ABAP ha la capacità di evolversi in base alle tecnologie e alle necessità emergenti. Nei primi anni di ABAP come linguaggio di quarta generazione (anni ’80), veniva principalmente utilizzato per creare report sulla piattaforma SAP R/2. Con l’arrivo di SAP R/3 (anni ’90), il linguaggio fu potenziato affinché sia SAP sia i clienti potessero usarlo per creare programmi ed estensioni. Con service pack, enhancement pack e upgrade di release, il linguaggio ABAP si è evoluto continuamente per rispondere alle esigenze del momento. Sebbene il passaggio al cloud computing sia stato un cambiamento fondamentale, la strategia di SAP per ABAP si basa su “evoluzione, non rivoluzione”, il che significa che le modifiche apportate ad ABAP per adattarlo al cloud computing sono state precise, controllate, ben ponderate e incrementali. Soprattutto, le esigenze dei clienti sono sempre state prioritarie.
Una precedente evoluzione di ABAP
A questo proposito, prima di analizzare i cambiamenti ad ABAP resi necessari dal cloud computing, vale la pena considerare una situazione precedente in cui ABAP dovette evolversi a seguito di un cambiamento di paradigma: l’emergere dei concetti orientati agli oggetti che raggiunsero un uso diffuso negli anni ’90. Fino a quel momento, il linguaggio ABAP era di natura procedurale. Una volta che divenne evidente la necessità di supportare concetti orientati agli oggetti, furono aggiunte diverse parole chiave al linguaggio per permettere agli sviluppatori di implementare tali concetti. Queste parole chiave furono costruite con cura per evolvere il linguaggio ABAP rispettando al contempo il codice ABAP esistente nei sistemi dei clienti, minimizzando così le interruzioni. Di conseguenza, uno sviluppatore ABAP poteva scrivere sia codice procedurale sia orientato agli oggetti e aveva la flessibilità di decidere il giusto equilibrio tra i due per ogni compito. Ad esempio, se un’azienda si poneva l’obiettivo di avere il 90% del proprio codice ABAP custom orientato agli oggetti entro una certa data, questo poteva essere realizzato al ritmo desiderato, anziché imposto dall’alto. Questo punto è importante: ABAP è sempre evoluto in modo generalmente “retrocompatibile”. Ciò significa che le modifiche guardano al futuro, senza che il codice esistente debba essere adattato per rispettare nuovi standard o funzionalità. Gli sviluppatori utilizzano semplicemente le nuove funzionalità nei progetti futuri.
Il Modello di Sviluppo ABAP Cloud (ABAP Cloud)
L’emergere e l’uso diffuso del cloud computing, del cloud native e delle REST API hanno generato un’ulteriore necessità di evoluzione per ABAP. Questa esigenza si è concretizzata nel modello di sviluppo ABAP Cloud (ABAP Cloud). I vari aspetti e componenti di ABAP Cloud forniscono tutto ciò di cui uno sviluppatore ABAP ha bisogno in un contesto cloud-native. Le principali caratteristiche di ABAP Cloud sono le seguenti:
    • Un linguaggio cloud native: ABAP per lo sviluppo Cloud – una versione di ABAP ottimizzata per il cloud
    • Modelli di programmazione cloud native: ABAP RESTful application programming model e ABAP analytics
    • Funzionalità Platform as a Service (PaaS) come parte della piattaforma ABAP: servizi di riuso, gestione di identità e accessi e connettività
    • Funzionalità integrate di SAP S/4HANA Cloud: Business API, extension points ed eventi
    • Strumenti: ABAP Development Tools per Eclipse come ambiente di sviluppo integrato
Al centro del modello di sviluppo ABAP Cloud c’è il suo modello di programmazione, che definisce l’architettura a design-time e runtime di tutte le estensioni, servizi e applicazioni. Quando si parla del modello di programmazione, generalmente si considerano i seguenti tre casi d’uso o scenari:
    • Transazionale (OLTP): Con ABAP Cloud è possibile costruire business object ed esporli come servizi per consumarli in UI e scenari di integrazione. Tutti i comportamenti standard sono supportati (create, read, update, delete). Un esempio noto è il business object Sales Order. Queste funzionalità si ottengono usando l’ABAP RESTful application programming model.
    • Analitico (OLAP): ABAP Cloud è altrettanto attrezzato per creare servizi e UI per l’analisi dei dati, per drill-down su più dimensioni, ecc. Un caso d’uso primario è l’integrazione dei dati in SAP Analytics Cloud. Questa funzionalità è resa possibile usando ABAP analytics.
    • Integrazione: Entrambi gli aspetti precedenti sono completati da una forte integrazione dei dati e delle applicazioni per rispondere agli ambienti orientati ai servizi odierni.
Il modello di programmazione non è isolato: è accompagnato da due differenziatori chiave:
    • Servizi e librerie riutilizzabili con servizi core di business come number ranges, application jobs, un SAP Fiori launchpad e un repository UI integrato per distribuire UIs SAPUI5 e SAP Fiori elements.
    • Qualità integrate che offrono estendibilità end-to-end nel modello di programmazione, principali qualità cloud come scalabilità e stabilità agli upgrade, e molte altre.
L’evoluzione verso ABAP Cloud

ABAP Cloud è il risultato di una serie di innovazioni avvenute nell’ultimo decennio. Gli ABAP Development Tools per Eclipse sono stati introdotti nel 2012, offrendo agli sviluppatori un ambiente aggiuntivo per costruire, debugare, testare ed eseguire il loro codice ABAP. Poco dopo, sono stati introdotti i Core Data Services, fornendo agli sviluppatori un modo dichiarativo per creare modelli di dati da utilizzare nella costruzione di applicazioni ottimizzate per SAP HANA. REST, emerso come uno stile architetturale ampiamente utilizzato, come abbiamo esplorato nell’unità precedente, ha portato allo sviluppo dell’ABAP RESTful application programming model, che consente agli sviluppatori ABAP di creare in modo efficiente servizi REST end-to-end basati su ABAP per lo sviluppo di applicazioni SAP Fiori transazionali e Web API.
Ognuna di queste innovazioni, singolarmente, ha un grande valore. Ma, come si dice spesso, “il tutto è maggiore della somma delle parti”. Lo stesso vale qui. ABAP Cloud non solo unisce tutte queste innovazioni, ma aggiunge anche diverse ulteriori innovazioni combinandole in modo olistico. Di conseguenza, gli sviluppatori possono ora beneficiare di uno sviluppo cloud native end-to-end efficiente utilizzando ABAP. ABAP Cloud può essere utilizzato per sviluppare applicazioni e servizi custom, così come per creare estensioni alle applicazioni SAP S/4HANA Cloud.
Disponibilità di ABAP Cloud

ABAP Cloud è disponibile come opzione predefinita (e unica) sia in SAP BTP, ambiente ABAP, sia in SAP S/4HANA Cloud Public Edition. Per entrambe le versioni, SAP S/4HANA Cloud Private Edition e SAP S/4HANA, ABAP Cloud coesiste con ABAP Classic e i clienti possono scegliere quando utilizzare ciascun modello, i dettagli dei quali saranno trattati nell’Unità 5, Evaluating Special Considerations for SAP S/4HANA Cloud Private Edition and SAP S/4HANA. Anche in questo caso, evoluzione, non rivoluzione.

In precedenza, nell’Unità 2, Lezione 2, Evaluating SAP Build, abbiamo esplorato la differenza tra il “citizen developer” (cioè un “builder”) e lo sviluppatore più tradizionale, in termini di supporto agli strumenti. I builder necessitano di strumenti che rientrano principalmente nella categoria “low code”, mentre gli sviluppatori richiedono un set di strumenti più orientato al “pro-code”. ABAP Cloud è orientato alla persona sviluppatore.
Linguaggio ABAP Ottimizzato per il Cloud

A causa della sua lunga e ricca storia, esiste un ampio numero e varietà di keyword, artefatti e tecniche ABAP che forniscono funzionalità necessarie per lo sviluppo di applicazioni enterprise professionali. Tuttavia, non tutti questi elementi sono compatibili con le esigenze di un approccio cloud native, quindi solo un sottoinsieme di essi è utilizzato in ABAP Cloud. Ad esempio, keyword obsolete come l’istruzione TABLES sono proibite. Anche Dynpro e Web Dynpro sono proibiti, sostituiti dalle UI SAP Fiori basate su servizi REST creati utilizzando l’ABAP RESTful application programming model. Le istruzioni SELECT direttamente sulle tabelle SAP sono proibite, sostituite dall’uso dei Core Data Services.
Per chiarire questa differenza, gli sviluppatori devono ora assegnare la versione del linguaggio agli oggetti di sviluppo al momento della loro creazione. Tale versione può essere “Standard ABAP” (“ABAP Classic”), “ABAP For Cloud Development” (per lo sviluppo ABAP Cloud) o “ABAP for Key Users” (anch’essa per lo sviluppo ABAP Cloud; da trattare nella prossima unità). Assegnando esplicitamente la versione, possono essere eseguiti i controlli appropriati per garantire che il lavoro di sviluppo sia conforme ad ABAP Cloud.
ABAP Development Tools per Eclipse

Tradizionalmente, gli sviluppatori utilizzavano l’ABAP Workbench per creare i vari artefatti necessari a un’applicazione, oltre a verificarne la sintassi e il debug. Come menzionato in precedenza, nel 2012 è stata introdotta la piattaforma Eclipse insieme a un plugin speciale, gli ABAP Development Tools per Eclipse, come ambiente alternativo “pro-code” per lo sviluppo ABAP. Lo sviluppo ABAP Cloud viene effettuato esclusivamente utilizzando gli ABAP Development Tools per Eclipse. Questi strumenti verificano la compatibilità con ABAP Cloud tramite una combinazione di controlli del compilatore ABAP, del runtime ABAP e dell’ABAP Test Cockpit, secondo necessità. Queste funzionalità, combinate con le caratteristiche già esistenti e familiari degli ABAP Development Tools per Eclipse, come completamento del codice, controllo della sintassi e debug, rendono la transizione allo sviluppo ABAP Cloud fluida e semplice per gli sviluppatori. Per ulteriori informazioni su come abilitare una migrazione agevole dall’ABAP Workbench agli ABAP Development Tools per Eclipse, consultare le FAQ SE80 Experts Using ADT.

Describing The Different Use Cases For ABAP Cloud
I diversi casi d’uso per lo sviluppo utilizzando il modello di sviluppo ABAP Cloud

ABAP Cloud - Casi d’uso transazionali (OLTP): il modello di programmazione ABAP RESTful

Abbiamo visto come il cloud native abbia richiesto un’evoluzione del linguaggio di programmazione ABAP (versione del linguaggio ABAP “ABAP for Cloud Development” o “ABAP for Key Users” rispetto ad “ABAP Classic”) e dell’IDE principale (ABAP development tools per Eclipse). Quindi, non sarà una sorpresa che anche il modello di programmazione principale utilizzato da ABAP dovesse evolversi. Le tecnologie ABAP classiche come SAP GUI o Web Dynpro non sono compatibili con le esigenze del cloud native.
Come menzionato nella lezione precedente, REST è emerso come uno dei modelli architetturali API più popolari utilizzati oggi dagli sviluppatori, e una delle implementazioni più comuni di REST è l’Open Data Protocol (OData). Spesso definito “ODBC per il Web”, OData è progettato da zero per ottimizzare il tipo di elaborazione e manipolazione dei dati di cui un programma aziendale ha bisogno. Pur non essendo tecnicamente obbligatorio, nella maggior parte dei casi i dati aziendali manipolati tramite OData risiedono in un database. Poiché il database SAP HANA è il database sottostante per SAP S/4HANA Cloud, REST in generale e OData in particolare sono direzioni naturali per un modello di programmazione ABAP evoluto che tenga conto delle esigenze del cloud native. Il risultato di questa evoluzione è il modello di programmazione ABAP RESTful.
Ma prima c’è stata una piccola tappa intermedia.
La prima generazione di servizi OData compatibili con REST si basava sul modello di programmazione precursore del modello ABAP RESTful, il ABAP Programming Model for SAP Fiori. Sebbene al momento della sua creazione questo modello fosse considerato una best practice per la creazione di servizi, c’erano alcune sfide. Lo sviluppo utilizzando l’ABAP Programming Model for SAP Fiori in scenari brownfield non era supportato e il supporto degli strumenti consisteva in diversi codici di transazione anziché in un ambiente di sviluppo unificato. Inoltre, alcuni aspetti del modello di programmazione utilizzavano un’implementazione di framework che offriva una trasparenza leggermente inferiore rispetto al codice ABAP a cui gli sviluppatori ABAP erano abituati.
Sebbene queste sfide fossero gestibili, il passo evolutivo successivo è stato quello di eliminarle consolidando l’intero flusso di sviluppo in Eclipse con ABAP development tools per Eclipse e semplificando e consolidando gli artefatti di sviluppo in un elenco semplice e intuitivo. Il modello di programmazione ABAP RESTful è il successore dell’ABAP Programming Model for SAP Fiori ed è il modello di programmazione utilizzato in ABAP Cloud per i casi d’uso transazionali.
Il modello di programmazione ABAP RESTful permette la creazione di servizi OData compatibili con REST a partire da un numero ridotto di artefatti semplici e intuitivi. Questi servizi possono essere utilizzati sia come livello di servizio per le app SAP Fiori eseguite al livello utente, sia come Web API standalone (consumabile da qualsiasi tipo di client, sia UI-based che no). Gli oggetti aziendali costruiti con il modello di programmazione ABAP RESTful possono essere utilizzati come API locali (di cui si parlerà a breve).
Nella lezione precedente, abbiamo menzionato che un design a microservizi, dove un’applicazione è suddivisa in un livello utente separato, un livello di servizio e un livello dati, è un elemento importante dello sviluppo cloud native. Il modello di programmazione ABAP RESTful è progettato da zero per essere coerente con il concetto di microservizi.
Modello di programmazione ABAP RESTful
Gli artefatti del modello di programmazione ABAP RESTful sono organizzati attorno ai seguenti quattro livelli:
    • Accesso ai dati (Data Access)
    • Modello di dominio e implementazione (Domain Model and Implementation)
    • Esposizione dei servizi aziendali (Business Service Exposure)
    • Consumo dei servizi aziendali (Business Service Consumption)
Vediamo i diversi livelli.
Accesso ai dati
Alla base del modello di programmazione ABAP RESTful ci sono le tabelle di database, che contengono i dati aziendali necessari per transazioni e analisi. Quel database è naturalmente SAP HANA. Utilizzando SAP HANA, il modello ABAP RESTful beneficia automaticamente dell’architettura in-memory, dell’archiviazione columnar, dei dati in tempo reale e della tecnologia di machine learning, tra le altre tecnologie.
Modello di dominio e implementazione
Il modello di dominio e l’implementazione comprendono la rappresentazione dei diversi concetti coinvolti in uno scenario aziendale (ad esempio clienti e ordini), le loro relazioni (ad esempio la relazione genitore-figlio tra clienti e ordini) e infine l’implementazione di queste entità e relazioni.
Programmazione specifica per dominio
Il linguaggio ABAP e gli ABAP Core Data Services (CDS) sono i principali linguaggi utilizzati per fornire l’implementazione specifica per dominio di query in sola lettura e oggetti aziendali transazionali nel contesto del modello di programmazione ABAP RESTful.
La versione del linguaggio ABAP “ABAP for Cloud Development” fornisce costrutti ottimizzati per il cloud utilizzati nel contesto di ABAP Cloud per implementare la logica aziendale. Il linguaggio ABAP è arricchito con un Entity Manipulation Language (EML) per controllare nativamente il comportamento transazionale degli oggetti aziendali costruiti con il modello ABAP RESTful.
I CDS forniscono un’infrastruttura potente di modellazione dati per definire modelli di dati semanticamente ricchi sul server applicativo ABAP. I vari artefatti CDS sono definiti utilizzando:
    • CDS Type Definition Language (TDL)
    • CDS Data Definition Language (DDL)
    • CDS Service Definition Language (SDL)
    • CDS Data Control Language (DCL)
    • CDS Annotations
Modellazione dei dati specifica per dominio
I modelli specifici per dominio determinano gli artefatti di design time del modello di dati a seconda dell’aspetto del modello di programmazione. È possibile sviluppare query in sola lettura e oggetti aziendali transazionali con il modello ABAP RESTful. Ogni entità del mondo reale è rappresentata da un oggetto aziendale (BO), che consiste in uno o più nodi con una relazione genitore-figlio tra i nodi. Un oggetto aziendale inizia sempre con un nodo radice.
Prendendo l’esempio clienti e ordini, per ciascuno di essi esistono due possibilità nel modello ABAP RESTful: scenari in sola lettura (cioè funzionalità di query) e scenari transazionali (cioè creazione, aggiornamento e cancellazione). Le query sono modellate usando ABAP CDS. La funzionalità transazionale è definita con una CDS behavior definition insieme al linguaggio ABAP e anche a EML. A livello concettuale, quindi, un BO consiste in un modello dati definito con entità ABAP CDS e nella capacità transazionale associata definita con una CDS behavior definition e implementata con linguaggio ABAP ed EML. Il modello dati di ciascun nodo BO è rappresentato da una CDS view entity definita su una tabella dati o altre entità CDS. Quindi, in uno scenario clienti / ordini, ad esempio, ci sarebbero due principali CDS view entity, una per ciascuno rispettivamente.
Esposizione dei servizi aziendali
Un servizio aziendale è dove le capacità REST del modello ABAP RESTful prendono forma. Consiste in:
    • Una service definition che espone le capacità di query e transazionali accessibili via REST.
    • Un service binding che associa una service definition a un protocollo REST, rendendo il servizio disponibile per il consumo.
    • Una service definition può essere pubblicata più volte da diversi service binding utilizzando protocolli differenti a seconda del tipo di consumo preferito.
Consumo dei servizi aziendali
Il consumo è possibile utilizzando diverse opzioni. Come menzionato in precedenza, un service binding basato su OData può abilitare lo sviluppo di app SAP Fiori. OData può anche essere utilizzato per integrazione app-to-app (o system-to-system). In questo caso, qualsiasi metadata UI presente nel livello Domain Modeling and Implementation viene ignorato. L’architettura basata su eventi consente comunicazioni asincrone tra un provider di eventi e un consumer di eventi in scenari dove non è richiesta una risposta diretta dal consumer. Utilizzando SAP Event Mesh, un servizio in SAP BTP, un BO del modello ABAP RESTful può agire come event consumer o event provider.
ABAP Cloud – Casi d’uso analitici (OLAP)

Oltre ai suoi casi d’uso transazionali, ABAP Cloud è all’altezza anche degli scenari analitici. I casi d’uso analitici prevedono l’analisi e la valutazione di modelli di dati multidimensionali per derivare decisioni aziendali basate su dati in tempo reale. L’aspetto del modello di programmazione analitico si concentra sulla creazione di modelli di dati per analizzare i dati aziendali in contesti embedded o cross-system e per visualizzare i dati in dashboard o come parte di applicazioni.
Lo sviluppo end-to-end per questi casi d’uso analitici è possibile utilizzando ABAP Cloud. I provider analitici, come uno schema a stella o a fiocco di neve riutilizzabile (basato su cubi, dimensioni e gerarchie), possono essere progettati per costruire modelli multidimensionali specifici per dominio. La logica specifica per dominio è implementata con CDS. Il CDS analytical provider può essere esposto utilizzando il servizio Information Access (InA) protocol per diversi client analitici, come SAP Analytics Cloud o SAP Analysis for Office. Inoltre, è possibile l’esposizione tramite OData per l’accesso tramite interfacce SAP Fiori.
ABAP Cloud – Casi d’uso di integrazione

L’Impresa Intelligente e Sostenibile
Infine, analizziamo i casi d’uso di integrazione. Per comprendere questo scenario è utile definire il termine intelligent, sustainable enterprise. Un’impresa intelligente e sostenibile è quella che applica costantemente tecnologie avanzate e best practice all’interno di processi aziendali agili e integrati. SAP supporta i propri clienti nel diventare imprese intelligenti fornendo soluzioni per integrare dati e processi, costruire catene del valore flessibili, innovare con le best practice di settore, comprendere e agire sul sentiment di clienti, partner e dipendenti, e gestire l’impatto ambientale. Combinando il portfolio completo di prodotti SAP, come SAP S/4HANA Cloud e SAP Ariba, insieme a SAP Business Technology Platform, SAP possiede la capacità unica di integrare i processi aziendali end-to-end.
L’impresa intelligente di SAP consiste nei seguenti quattro processi core end-to-end:
    • Lead To Cash
    • Design To Operate
    • Source To Pay
    • Recruit To Retire
Ciascuno di questi processi richiede connettività tra diversi prodotti e soluzioni SAP, incluso SAP S/4HANA Cloud. Di conseguenza, le opzioni di connettività continuano a essere necessarie e sono fornite come parte di ABAP Cloud. Le tecnologie di integrazione deprecate non possono più essere utilizzate in ABAP Cloud (ad esempio, IDoc) – possono essere usati solo framework rilasciati. I framework di connettività disponibili sono:
    • Servizi OData
    • Business Events
    • Servizi HTTP

Per garantire la separazione dei contenuti tra credenziali, i clienti non hanno accesso diretto alle transazioni classiche per le destinazioni (SM59) e ai porti logici (SOAMANAGER) in SAP S/4HANA Cloud. Al loro posto, una serie di app SAP Fiori (note come Cloud Communication Management) viene utilizzata per configurare tutti gli artefatti logici necessari per implementare scenari di comunicazione insieme alle opzioni utente e di autenticazione necessarie.
Modello di Sviluppo ABAP Cloud vs Modello di Programmazione ABAP RESTful
Concludiamo questa lezione riconoscendo che a prima vista potrebbe sembrare che i termini ABAP Cloud development model e ABAP RESTful application programming model si riferiscano allo stesso concetto. Non è così. I due termini si riferiscono a concetti differenti, cosa importante da comprendere.
L’ambito di ciò a cui si riferisce ABAP Cloud è più ampio. Include il modello completo di sviluppo. Questo comprende (ma non si limita a) modelli di programmazione, specifiche del ciclo di vita, API, regole per lo sviluppo custom e di estensione e persino dettagli relativi alla gestione dell’identità e degli accessi.
L’ambito a cui si riferisce il modello di programmazione ABAP RESTful, invece, è più ristretto e specifico. Si riferisce a un modello di programmazione specifico (cioè strumenti, tecnologie e tecniche) per costruire artefatti di sviluppo specifici per scopi specifici. Il modello di programmazione è parte di ABAP Cloud ed è incorporato in esso. È altrettanto corretto definire la relazione in senso inverso (cioè ABAP Cloud utilizza ABAP RESTful application programming model per implementare casi d’uso transazionali, analitici e di integrazione).

API rilasciate: API della piattaforma ABAP locale

Come menzionato nell’Unità 1 Lezione 2, Introduzione all’Approccio Clean Core, una delle parti più importanti del concetto di clean core è l’uso di interfacce stabili agli aggiornamenti in SAP S/4HANA Cloud. Questo contribuisce a rendere gli aggiornamenti software, quando applicati, fluidi e semplici senza interruzioni.
Per sfruttare questo vantaggio, sia SAP sia i clienti collaborano. Da parte di SAP, SAP fornisce interfacce pubblicate, costituite da diversi tipi. Inoltre, SAP garantisce la stabilità di queste interfacce da una release all’altra, in modo che i clienti possano utilizzarle con sicurezza. Da parte del cliente, i clienti accettano di usare solo le interfacce pubblicate sia nei loro nuovi sviluppi (artefatti creati dal cliente) sia negli sviluppi di estensione (implementazioni di estensione). In realtà, questo è applicato tramite controlli di sintassi e controlli dell’ABAP Test Cockpit negli strumenti di sviluppo ABAP per Eclipse come parte del modello di sviluppo ABAP Cloud, i dettagli del quale saranno discussi nella prossima unità.
Queste interfacce pubblicate hanno origine da diverse fonti. La prima è la piattaforma ABAP cloud disponibile in SAP BTP, ambiente ABAP, e anche in SAP S/4HANA Cloud, ambiente ABAP. Sono comunemente indicate come API della piattaforma ABAP locale. Poiché entrambi i prodotti utilizzano la stessa linea di codice della piattaforma ABAP cloud, un oggetto SAP (come un elemento di dati, ad esempio) che è pubblicato è disponibile in entrambi i contesti. In questo modo, gli sviluppatori possono collocare il codice dove ritengono più opportuno, o anche in entrambi i contesti, se questo è l’approccio preferito.
Riconoscendo che in un mondo cloud-native alcuni oggetti SAP potrebbero non essere adatti, SAP li ha sistematicamente sostituiti con equivalenti progettati per il cloud.
SAP S/4HANA Cloud Business APIs

Consumo Remoto
Esistono diversi tipi di interfacce pubblicate disponibili per l’utilizzo in SAP S/4HANA Cloud e un buon modo per comprenderle è analizzarle in base allo scopo.
Il primo scopo è rappresentato dalle interfacce destinate ad essere consumate da sorgenti remote (non SAP S/4HANA Cloud), come applicazioni personalizzate eseguite su SAP BTP. Queste interfacce (comunemente denominate remote API) possono essere servizi OData creati utilizzando il modello di programmazione ABAP RESTful, così come servizi SOAP. Abbiamo esplorato come i servizi OData possano essere consumati sia da SAP Fiori sia da SAP Build Apps nello sviluppo di applicazioni. Entrambi questi casi erano scenari di chiamata diretta (sincrona) avviati direttamente dall’applicazione. Tuttavia, molte applicazioni sono progettate come asincrone (uno scenario di chiamata indiretta). In uno scenario asincrono, invece di comunicare direttamente, mittente e destinatario utilizzano un broker middleware per scambiarsi informazioni sotto forma di messaggi. Cloud Integration, una funzionalità all’interno di SAP Integration Suite, è un servizio che funziona su SAP BTP ed è progettato specificamente per essere utilizzato in questo tipo di scenario. Sono forniti sia un adattatore OData sia un adattatore SOAP, così che gli sviluppatori possano utilizzare rispettivamente i servizi OData e SOAP.
Eventi
Un altro servizio offerto come parte di SAP BTP è SAP Event Mesh, che consente alle applicazioni di comunicare tra loro tramite eventi asincroni. Questo tipo di comunicazione permette la progettazione di processi aziendali guidati da eventi. Con un’architettura basata su eventi, esiste un provider dell’evento che genera un evento e un consumatore dell’evento che viene notificato dell’evento e reagisce di conseguenza. SAP Event Mesh funge da “collante” tra provider e consumatore. Il modello di programmazione ABAP RESTful supporta nativamente il design basato su eventi e i BO del modello di programmazione ABAP RESTful possono funzionare sia come provider sia come consumatore, a seconda dello scenario progettuale.
Consumo Locale
Il secondo scopo è rappresentato dalle interfacce destinate ad essere consumate localmente (cioè basate su SAP S/4HANA Cloud). Il consumo di queste interfacce può avvenire tramite un’applicazione personalizzata costruita utilizzando il modello di programmazione ABAP RESTful, o tramite un’implementazione BAdI. Nella progettazione di questi consumi, gli sviluppatori possono utilizzare classi e viste CDS, tra le altre possibilità, per facilitare l’accesso alle funzionalità di SAP S/4HANA Cloud. Queste interfacce locali sono comunemente denominate local API. Per fare un semplice esempio di local API, normalmente, se uno sviluppatore avesse bisogno di accedere alla tabella dei paesi, selezionerebbe direttamente i dati dalla tabella T005. Tuttavia, esiste una vista CDS locale “I_country” (già pubblicata) che fornisce accesso a questi dati.
Local Extension Points
Infine, esistono interfacce utilizzate per scopi di estensione (local extension points). Simili alle local API, questi extension point esistono in SAP S/4HANA Cloud e gli sviluppatori vi creano le loro implementazioni di estensione. I BAdI, introdotti per la prima volta con SAP R/3 4.6(c), sono disponibili in SAP S/4HANA Cloud e con il modello di programmazione ABAP RESTful come modello preminente utilizzato da ABAP Cloud. È stato progettato anche un modello di estendibilità disponibile per gli sviluppatori.

Sia le API pubbliche locali e remote, sia i local extension point per SAP S/4HANA Cloud, sono visibili utilizzando SAP Business Accelerator Hub, che può continuare a essere usato a scopo di scoperta. Tuttavia, come opzione aggiuntiva, gli strumenti di sviluppo ABAP per Eclipse dispongono della vista degli oggetti rilasciati, che mostra allo sviluppatore cosa è specificamente rilasciato per l’uso nello sviluppo ABAP Cloud. Mentre SAP Business Accelerator Hub mostra le remote API, eventi, viste CDS, interfacce BO del modello di programmazione ABAP RESTful e BAdI, la vista degli oggetti rilasciati mostra ulteriori oggetti rilasciati per lo sviluppo, come elementi di dati, oggetti di autorizzazione e viste CDS.
Una funzionalità diversa ma strettamente correlata negli strumenti di sviluppo ABAP per Eclipse è la capacità di rilevare l’uso di API non rilasciate e, se è disponibile un sostituto adeguato, di generare un messaggio di errore di sintassi suggerendo quale sostituto utilizzare. Ad esempio, la tabella T005 (Paesi) non è rilasciata. Tuttavia, è disponibile una vista CDS sostitutiva I_COUNTRY. Qualsiasi accesso alla tabella T005 genera un errore di sintassi con il seguente messaggio:
L’uso della tabella T005 non è consentito. Utilizzare invece l’entità CDS I_COUNTRY.

Estendibilità Classica e il Problema che Presenta con il Cloud Native

Con SAP S/4HANA Cloud costruito da zero, in linea con i principi cloud native, non esistono progetti di aggiornamento specifici per il cliente. Gli aggiornamenti software vengono distribuiti a tutti i clienti contemporaneamente. Tuttavia, come menzionato in precedenza nell’Unità 1, Lezione 2, Introduzione all’Approccio Clean Core, l’estendibilità è una caratteristica importante e necessaria nelle soluzioni SAP e SAP S/4HANA Cloud non fa eccezione. L’estendibilità consente ai clienti di creare un vantaggio competitivo personalizzando i propri processi aziendali e permette ai partner di arricchire l’ERP con soluzioni su misura.
Le tecniche di estendibilità classica discusse nell’Unità 1, utilizzate in passato dai clienti, non sono coerenti con il cloud native. È necessario un framework evoluto – un framework che permetta ai clienti di continuare a ottenere vantaggio competitivo attraverso la differenziazione tramite estensioni, pur essendo in grado di ricevere gli aggiornamenti software di SAP S/4HANA Cloud in modo fluido e senza interruzioni. La risposta a questo è il modello di estendibilità di SAP S/4HANA Cloud, che aiuta i clienti a mantenere un core pulito anche quando costruiscono estensioni.

Explaining Key User Extensibility
Estendibilità per Key User

In precedenza, nell’Unità 2 Lezione 2, Valutazione di SAP Build, abbiamo discusso che l’emergere del citizen developer ha trasformato lo sviluppo delle applicazioni. L’estendibilità per key user è rivolta a coloro le cui personas rientrano nell’ambito dello sviluppo da parte dei citizen developer, cioè l’uso di strumenti low-code/no-code per portare a termine le proprie attività. Queste personas includerebbero quindi anche esperti di business, key user e potenzialmente altri tipi di ruoli.
Le opzioni di estendibilità per key user (precedentemente note come in-app) coprono un’ampia gamma di casi d’uso. Gli strumenti utilizzati per creare estensioni per key user non richiedono che il citizen developer comprenda alcun dettaglio tecnico sottostante dell’applicazione SAP che viene estesa. L’attenzione è rivolta a un’implementazione e un deployment rapidi di estensioni semplici utilizzando strumenti low-code/no-code. Tutti gli strumenti sono applicazioni Web-based SAP Fiori, disponibili in tutte le opzioni di deployment di SAP S/4HANA e, quando utilizzati, sono coerenti con l’approccio clean core.

In sintesi, gli strumenti e le funzionalità sono i seguenti:
    • Adattamento dell’Interfaccia Utente (UI) a Runtime: un key user può adattare un’interfaccia utente a runtime. Ad esempio, un’etichetta di campo può essere modificata con un valore specifico per paese, oppure può essere aggiunto un nuovo campo alla visualizzazione.
    • Campi Personalizzati: con questo strumento, un key user può creare e modificare campi personalizzati per tabelle SAP, viste Core Data Service (CDS) o servizi OData.
    • Logica Aziendale Personalizzata: questo strumento consente a un key user di estendere la funzionalità di SAP S/4HANA Cloud aggiungendo logica aziendale aggiuntiva. La logica viene inserita in un punto di enhancement sottostante (i dettagli sono nascosti al key user) e lo strumento include un editor ABAP Web-based con completamento del codice, controllo della sintassi e capacità di test.
    • Business Object (BO) Personalizzato: con questo strumento, i key user possono andare oltre la logica aziendale personalizzata. Possono creare interi BO nuovi insieme alle tabelle di database associate. Inoltre, può essere creata un’API per creare, leggere, aggiornare e cancellare i dati.
    • Vista CDS Personalizzata: un key user può utilizzare questo strumento per modellare l’accesso ai dati in modi che le viste CDS esistenti potrebbero non supportare, a supporto di reportistica o logiche aziendali personalizzate.
    • Query Analitiche Personalizzate: le query costituiscono una delle basi della reportistica. Lo strumento Custom Analytical Query consente ai key user di crearle facilmente basandosi su fonti dati SAP o create dal cliente.
    • KPI: simili alle query, i KPI sono una parte importante della reportistica. Con gli strumenti KPI, i key user possono progettare nuovi KPI visualizzati come tile nel SAP Fiori launchpad con funzionalità di drill-down.
    • Moduli/Formulari: infine, per supportare implementazioni di processi basati su moduli ed email, lo strumento Custom Forms consente ai key user di creare modelli di moduli ed email basati su fonti dati SAP come CDS views e servizi OData.

SAP S/4HANA Cloud Business Add-Ins (BAdI)

I SAP S/4HANA Cloud Business Add-Ins (BAdI) rappresentano un’opzione aggiuntiva di enhancement disponibile. Panorama di Sistema per l’Estendibilità On-Stack per Sviluppatori
Originariamente, SAP S/4HANA Cloud veniva fornito ai clienti con un landscape a due tenant: un tenant di qualità utilizzato per attività di sviluppo, configurazione e test, e un sistema di produzione, dove gli utenti finali lavoravano in modalità produttiva. Questa configurazione era sufficiente per l’estendibilità dei key user.
Tuttavia, poiché le implementazioni delle estensioni on‑stack per sviluppatori richiedono strumenti basati su ABAP insieme al codice ABAP associato, è necessaria una leggera modifica nella configurazione dei tenant. Simile al design tradizionale on-premise, vengono forniti ai clienti tenant separati per sviluppo, test e produzione in SAP S/4HANA Cloud. Sia le estensioni per key user sia quelle per sviluppatori vengono assegnate a trasporti per essere testate e utilizzate negli ambienti produttivi.
Estendibilità del Modello di Programmazione ABAP RESTful in SAP S/4HANA Cloud

Nell’Unità 3 Lezione 2, Esplorazione del Modello di Sviluppo ABAP Cloud (ABAP Cloud), abbiamo esaminato i vari artefatti del modello di programmazione ABAP RESTful, come i BO (Business Object) e le definizioni di servizio del modello ABAP RESTful, e come lo sviluppo ABAP Cloud utilizza questo modello. L’estendibilità del modello di programmazione ABAP RESTful diventa quindi uno dei modi in cui viene realizzata l’estendibilità per sviluppatori in SAP S/4HANA Cloud. L’estendibilità del modello ABAP RESTful offre ai clienti la possibilità di creare estensioni stabili rispetto agli aggiornamenti e al ciclo di vita per i BO del modello ABAP RESTful su ciascun livello dello stack del modello. Il BO originale del modello ABAP RESTful è sviluppato da SAP, e a ogni livello SAP può sia abilitare l’estendibilità sia specificare quali tipi specifici di estensioni sono consentiti. In generale, i tipi di estensioni possibili in tutto lo stack del modello ABAP RESTful sono i seguenti:
Estensioni del Modello Dati
Queste estensioni si presentano in due forme: estensioni di tabelle database e estensioni di viste CDS. Il concetto di aggiungere nuovi campi a una tabella database è familiare agli sviluppatori ABAP. Con l’estendibilità per sviluppatori, le tabelle create da SAP vengono esplicitamente rilasciate come estendibili tramite un’annotazione. SAP fornisce inoltre una struttura di estensione (anch’essa esplicitamente rilasciata come estendibile) in cui lo sviluppatore ABAP può inserire i nuovi campi, e questa struttura è esplicitamente referenziata dalla tabella. Per le viste CDS, se uno sviluppatore ABAP estende una tabella database con nuovi campi, tutte le entità CDS dipendenti da quella tabella vengono estese di conseguenza. Similmente al livello database, viene utilizzata una vista CDS creata da SAP e una vista di estensione collegata (entrambe esplicitamente rilasciate come estendibili). Questo assicura che la vista CDS sia a conoscenza e possa selezionare eventuali nuovi campi creati. Oltre ai nuovi campi, è consentita anche la modellazione di nuove associazioni.
Estensioni di Comportamento e Field Behavior
Questi tipi di estensione consentono allo sviluppatore ABAP di arricchire un BO del modello ABAP RESTful con nuovo comportamento. Alcune possibilità di estensione disponibili per i clienti includono:
    • Possibilità di aggiungere nuovi campi al modello originale del BO ABAP RESTful e utilizzarli in ulteriori mappature di campo
    • Possibilità di definire nuove azioni, determinazioni e validazioni nel BO originale del modello ABAP RESTful
    • Possibilità di definire e implementare un salvataggio aggiuntivo
    • Per i BO ABAP RESTful abilitati a draft, possono essere aggiunte nuove determine actions e può essere estesa l’azione Prepare fornita dal framework ABAP RESTful
Estensioni di Nodo e Definizione di Servizio
Strettamente correlate alle estensioni di campo e comportamento, le estensioni di nodo permettono di aggiungere ulteriori entità BO del modello ABAP RESTful a un BO esistente. Ad esempio, una tabella specifica del cliente che non era rappresentata nel BO ABAP RESTful fornito da SAP può comunque essere integrata come nuova entità BO estesa, utilizzando le estensioni di campo e comportamento descritte nella sezione precedente per assicurare che la logica di business sia correttamente implementata per la nuova entità BO. Abilitazione dell’Estendibilità versus Provisioning dell’Estendibilità
Nel comprendere le estensioni, la terminologia è importante per ridurre la confusione. Come per l’estendibilità classica, la determinazione se l’estendibilità sia consentita è effettuata da SAP, e pertanto si usa il termine extensibility enablement (abilitazione dell’estendibilità). L’effettivo utilizzo dell’estensione, cioè il "fare estensione", è effettuato dal cliente, e il termine di riferimento è extensibility provisioning (provisioning dell’estendibilità).

Explaining Side-By-Side Extensibility
Estensibilità affiancata

Le estensioni affiancate sono inoltre orientate verso la persona sviluppatore tradizionale. Queste estensioni non vengono eseguite su SAP S/4HANA Cloud, ma su SAP BTP, utilizzando i servizi di sviluppo e runtime che esso offre. Questo può essere Java, Node.js o l’ambiente ABAP di SAP BTP. Nella Lezione 2 dell’Unità 3, Esplorare il modello di sviluppo ABAP Cloud, abbiamo discusso di come SAP S/4HANA Cloud abbia sia interfacce locali sia interfacce pubbliche remote rilasciate. I dati sono quindi disponibili per essere utilizzati localmente da altri servizi SAP BTP, memorizzati localmente se desiderato, o combinati con dati aggiuntivi provenienti da altre fonti per reportistica e analisi.
Alcuni dei possibili casi d’uso per le estensioni affiancate sono i seguenti:
    • Applicazioni personalizzate che necessitano di accesso ai servizi SAP BTP come machine learning, AI, e così via
    • Applicazioni personalizzate che si integrano con diversi sistemi, sia on-premise sia cloud-based
    • Soluzioni SaaS sviluppate da partner
    • SAP BTP, Ambiente ABAP
Come accennato in precedenza, il modello di sviluppo ABAP Cloud è disponibile per tutte le possibilità di deployment di SAP S/4HANA, nonché disponibile nell’ambiente ABAP di SAP BTP. L’ambiente ABAP di SAP BTP è l’offerta Platform as a Service (PaaS) di SAP per ABAP. Oltre alle applicazioni affiancate, i clienti possono anche sviluppare le proprie applicazioni standalone, entrambe le quali possono beneficiare delle capacità multitenancy di SAP BTP. Come per SAP S/4HANA, un database SAP HANA è incluso con l’ambiente ABAP di SAP BTP. Gli sviluppatori utilizzano il modello di programmazione ABAP RESTful come modello di programmazione e gli strumenti di sviluppo ABAP per Eclipse come ambiente di sviluppo insieme all’opzione di linguaggio ABAP Cloud. Questo rende l’ambiente ABAP di SAP BTP una scelta naturale per lo sviluppo di estensioni affiancate.

Exploring Clean Core Extensibility Best Practices
1ª Generazione: Modello di Estendibilità a 3 Livelli (Ora in Sunset)

Sebbene il modello di estendibilità a 3 livelli originale sia ora in Sunset a favore del nuovo concetto Clean Core basato su livelli, questa sezione lo esaminerà brevemente, poiché comprenderlo è utile per afferrare l’evoluzione verso il nuovo approccio basato su livelli. Inoltre, il codice cliente progettato e implementato secondo le linee guida originali a 3 livelli (in particolare i wrapper di Tier 2) non deve necessariamente essere migrato al nuovo approccio basato su livelli.
L’approccio originale basato su livelli per lo sviluppo di estensioni cliente era centrato sui seguenti 3 livelli:
    • Tier 1 (ABAP Cloud): Il metodo preferito, a prova di futuro e sicuro in caso di aggiornamenti. Per tutto il nuovo sviluppo. Utilizza una versione ABAP ristretta e ottimizzata per il cloud e può accedere solo alle API SAP rilasciate.
    • Tier 2 (Cloud API Enablement): Il “ponte”. Per il wrapping del codice cliente esistente (da Tier 3) o di oggetti standard SAP non ancora rilasciati per Tier 1. Il suo scopo è creare un’API stabile e riutilizzabile da consumare in Tier 1.
    • Tier 3 (ABAP Classico): Il metodo “legacy” o tradizionale. Per codice esistente e estensioni complesse e profonde che non sono possibili in Tier 1. Questo codice era strettamente accoppiato al sistema, poteva risultare problematico in caso di aggiornamento ed era quindi consigliato usarlo solo come ultima risorsa.
Sebbene questo approccio abbia creato un framework pratico per i clienti, è stato comunque ritirato a favore di un approccio evoluto e ancora più flessibile.


2ª Generazione: Concetto Clean Core basato su Livelli

L’Evoluzione: Da un Approccio Flessibile a un Approccio Ancora Più Flessibile

Inizialmente, il messaggio “Clean Core” veniva spesso percepito come un principio binario, tutto o niente: “O sei clean oppure non lo sei.” Questo approccio, pur essendo efficace, ha comunque creato alcune sfide per i clienti, in particolare riguardo al fatto che alcune API, pur non essendo ufficialmente “rilasciate”, erano abbastanza stabili e difficilmente avrebbero causato problemi negli scenari di aggiornamento. Inoltre, nella pratica, è irrealistico aspettarsi che i clienti eliminino semplicemente tutto il loro codice personalizzato esistente.
Riconoscendo ciò, SAP ha evoluto il modello a 3 livelli per adottare un approccio più pragmatico basato su livelli, consentendo ai clienti la flessibilità di adottare un approccio più orientato al rischio nella gestione del proprio codice personalizzato. Questo approccio riconosce che non tutte le estensioni sono equivalenti e fornisce un quadro chiaro e strutturato per sviluppatori e architetti. Trasforma l’estendibilità Clean Core da una regola rigida in una roadmap concreta e operativa.
Panoramica del Modello di Estendibilità Clean Core
Il modello di estendibilità Clean Core mira a migliorare la trasparenza e ridurre il debito tecnico nelle estensioni di SAP S/4HANA. Lo fa nei seguenti modi:
    • Concetto Clean Core più flessibile con quattro livelli (A–D), dove il Livello A rappresenta la qualità più alta.
    • I clienti sono incoraggiati a estendere SAP S/4HANA Cloud Private Edition al livello più alto possibile.
    • Livelli Clean Core più elevati riducono il debito tecnico, semplificano gli aggiornamenti e si allineano alle best practice SAP.
    • Le estensioni vengono valutate in base alla tecnologia meno qualificata utilizzata al loro interno.
Come il Concetto dei Livelli Clean Core Migliora le Opzioni di Estendibilità per i Clienti
La transizione dal modello di estendibilità a 3 livelli al concetto Clean Core basato sui livelli migliora la valutazione dell’estendibilità in tre modi principali:
    • Classificazioni Pragmatiche: Il nuovo approccio basato sui livelli fornisce una distinzione più sfumata tra estensioni stabili per aggiornamento e estensioni rischiose.
    • ABAP Classico: Gli oggetti ABAP classici non sono più uniformemente categorizzati come ad alto rischio, consentendo una valutazione più flessibile.
    • Il Meglio di Entrambi i Mondi: Il concetto dei livelli Clean Core riconosce il valore sia del codice legacy sia delle estensioni moderne, promuovendo al contempo il decoupling.
Come Funzionano i Livelli?
I livelli Clean Core classificano le estensioni in base alla loro conformità agli standard SAP per la stabilità negli aggiornamenti:
    • Livello A: Le estensioni utilizzano API rilasciate e sono completamente supportate da SAP, garantendo la massima stabilità agli aggiornamenti.
    • Livello B: Le estensioni sfruttano API e tecnologie classiche, offrendo un ambito più ampio per le personalizzazioni.
    • Livello C: Le estensioni accedono a oggetti interni, comportando rischi gestibili e consentendo esigenze specifiche del cliente.
    • Livello D: Le estensioni utilizzano oggetti non raccomandati, rappresentando il rischio e il debito tecnico più elevati.
Esploriamo questi concetti.
Un Nuovo Sistema di Classificazione
Il paragrafo precedente ha evidenziato l’insieme completo dei termini utilizzati per classificare gli oggetti ABAP:
    • API Rilasciate: Stabili, supportate e sicure per clienti e partner per la creazione di estensioni. Sono sicure agli aggiornamenti per progettazione.
    • API Classiche: Artefatti ABAP classici che, pur non essendo basati sugli ultimi framework, sono riconosciuti come sicuri per gli aggiornamenti e classificati come tali.
    • Oggetti Interni: Artefatti non classificati come “API Classiche”. Un approccio basato sul changelog consente alle organizzazioni di valutare in anticipo il rischio di aggiornamento degli “Oggetti Interni”, supportando decisioni informate prima di grandi progetti di aggiornamento.
    • Oggetti Non Raccomandati: Artefatti noti per introdurre sfide negli aggiornamenti, aiutando i clienti a evitare estensioni rischiose all’inizio dei loro progetti.
Livello A: Estensioni Clean basate su API Rilasciate


Panoramica Livello A:
    • Massimo standard nell’estendibilità SAP.
    • Garantisce soluzioni pronte per il futuro con stabilità massima agli aggiornamenti.
    • Utilizza API rilasciate, punti di estensione, tecnologie moderne, framework e pattern di sviluppo.
    • Allineato alla visione Clean Core di SAP.
Copertura:
    • Include solo estensioni basate su API SAP rilasciate e punti di estensione.
    • Si applica sia alle implementazioni side-by-side su SAP BTP (SAP Build per CAP e ABAP Cloud) sia allo sviluppo on-stack all’interno dei sistemi SAP S/4HANA.
    • Le estensioni on-stack devono utilizzare strumenti di estendibilità per key user o sviluppatori con le versioni ABAP pertinenti.
    • Non copre l’intero ambito di SAP S/4HANA Cloud Private Edition.
Coinvolgimento SAP:
    • Le estensioni si basano su oggetti SAP ufficialmente rilasciati e regolati da contratti di stabilità.
    • Interfacce e punti di estensione possono essere trovati in SAP Business Accelerator Hub, nel Cloudification Repository e direttamente nel sistema.
SAP S/4HANA Cloud Public Edition:
    • Il Livello A è allineato all’approccio di sviluppo per SAP S/4HANA Cloud Public Edition.
    • Le estensioni on-stack create per SAP S/4HANA Private Edition generalmente richiedono adattamenti per essere portabili sulla public cloud.
    • Le estensioni side-by-side su SAP BTP hanno maggiori probabilità di essere compatibili con la public cloud, poiché disaccoppiano la logica di business dal sistema core.
    • La parità completa non è garantita a causa delle differenze nella disponibilità delle API e nell’ambito applicativo tra le versioni di SAP S/4HANA.
Livello B: Utilizzo di API Classiche

Panoramica Livello B:
    • Risponde a requisiti non soddisfatti solo dalle API rilasciate.
    • Utilizza “API classiche” ben consolidate, ampiamente raccomandate e documentate.
    • Offre un ambito più ampio per miglioramenti di processo e personalizzazioni rispetto al Livello A.
    • Segue le best practice SAP per la stabilità agli aggiornamenti.
    • Le estensioni beneficiano della garanzia di qualità interna SAP e rappresentano opzioni a basso rischio.
Idoneità:
    • Le estensioni qualificano per il Livello B quando utilizzano solo oggetti SAP e pattern di sviluppo classificati come API classiche o API rilasciate.
    • Questo include:
        ◦ Wrapper attorno ad API classiche per facilitarne l’uso nelle applicazioni Livello A (es. utilizzo di BAPI_PO_CREATE1).
        ◦ Estensioni ABAP classiche, come implementazioni ABAP List Viewer in ambienti Dynpro o Web Dynpro usando API classiche come CL_GUI_ALV_GRID.
        ◦ Oggetti personalizzati sviluppati con la versione ABAP “Standard”, senza fare riferimento a oggetti SAP ristretti o non supportati.
    • Le estensioni Livello B mantengono un alto grado di stabilità agli aggiornamenti aderendo a pratiche di sviluppo consolidate.
Coinvolgimento SAP:
    • Include oggetti e punti di estensione esplicitamente nominati dagli esperti SAP come API classiche, pur senza contratti di stabilità formali.
    • Comprende una vasta gamma di API legacy, user exits, BAdI e framework consolidati come SAP GUI e ABAP List Viewer grid, esposti per l’uso cliente in SAP S/4HANA on-premise e SAP ERP.
    • Dove le API rilasciate non sono disponibili, le API classiche e i punti di estensione offrono l’opzione di estendibilità migliore successiva.
    • Una risorsa chiave per identificare API classiche e tecnologie di estensione è il Cloudification Repository (spiegato nella lezione successiva).
Livello C: Utilizzo di Oggetti Interni


Panoramica di livello C:

Implica l'uso di oggetti interni SAP non destinati all'uso da parte del cliente.
Questi oggetti non sono ufficialmente rilasciati, consigliati o pronti per il cloud e non rientrano nell'ambito di supporto formale di SAP.
La documentazione potrebbe essere incompleta o assente, senza garanzie di stabilità o utilizzo a lungo termine.
Offre capacità tecniche avanzate ma comporta rischi per la stabilità dei futuri aggiornamenti.
Il nuovo changelog per gli oggetti SAP consente ai clienti di analizzare e pianificare i potenziali impatti degli aggiornamenti.
Idoneità:

Le estensioni rientrano nel Livello C quando si utilizzano oggetti o modelli di sviluppo che non sono né formalmente rilasciati (Livello A) né nominati come maturi (Livello B).
Gli esempi includono l'uso diretto di moduli funzionali interni, classi o accesso in sola lettura a tabelle SAP non approvate per il consumo esterno.
Queste estensioni soddisfano requisiti specifici dei clienti non coperti da API di livello superiore, ma presentano il rischio di incompatibilità future.
Coinvolgimento SAP:

Copre gli oggetti SAP non designati come API rilasciate o classiche e non classificati esplicitamente come non consigliati.
Gli oggetti interni sono soggetti a modifiche senza preavviso o garanzie di compatibilità.
SAP può riclassificare gli oggetti interni come "API classiche" o "Non consigliate", spostando il livello (rispettivamente in B o D).
Questi cambiamenti sono determinati dal feedback dei clienti, dall'evoluzione delle strategie di prodotto o dalle sfide di aggiornamento osservate.
Changelog per oggetti SAP:

Introdotto per migliorare la trasparenza e supportare i clienti nella gestione dei rischi di Livello C.
Le caratteristiche includono:
Controlli automatizzati della cabina di pilotaggio per analizzare il codice personalizzato e rilevare modifiche incompatibili.
Accesso anticipato alle informazioni su futuri cambiamenti incompatibili.
Maggiore affidabilità e trasparenza della pianificazione per un’allocazione tempestiva delle risorse.
Incoraggia gli sviluppatori a riorganizzare le estensioni verso API rilasciate o classiche, ove possibile.
L'adozione del changelog aiuta a ridurre al minimo i rischi di aggiornamento, a ottenere una gestione proattiva delle modifiche e a garantire transizioni più fluide tra le versioni del software SAP.
Livello D: Core non pulito

Panoramica di livello D:

Rappresenta la categoria di rischio più elevata all'interno del concetto di livello di nucleo pulito.
Associato a notevoli debiti tecnici, sforzi di manutenzione e rischi per la stabilità del sistema, l'integrità dei dati e l'agilità aziendale.
Compromette l'innovazione a causa di problemi di compatibilità.
Si raccomanda vivamente di procedere immediatamente alla riparazione per allinearsi alle linee guida di supporto di SAP e garantire l'affidabilità operativa a lungo termine.
Idoneità:

Le estensioni rientrano nel Livello D quando si utilizzano oggetti SAP o modelli di sviluppo contrassegnati esplicitamente come non consigliati.
Gli esempi includono:
Modifiche, estensioni e operazioni di scrittura non supportate sulle tabelle SAP.
Miglioramenti impliciti.
Utilizzo di oggetti designati come fuori ambito per il consumo del cliente.
Coinvolgimento SAP:

Comprende tutti gli oggetti e i modelli ufficialmente dichiarati non raccomandati per uso esterno.
Include oggetti etichettati con la designazione "noAPI", identificabili nel Cloudification Repository filtrando lo "stato" impostato su "noAPI" Ciò verrà dimostrato nell'esercizio seguente.
Copre modifiche, determinati modelli di utilizzo degli oggetti (come l'accesso diretto in scrittura alle tabelle principali SAP) e tecniche di sviluppo sconsigliate come i miglioramenti impliciti.
Fornisce trasparenza tramite un elenco completo di oggetti e modelli sconsigliati per aiutare i clienti a identificare ed eliminare questi elementi ad alto rischio dai loro scenari SAP.

Exploring Clean Core Extensibility Best Practices — Exam Summary
First Generation: 3-Tier Extensibility Model (Now in Sunset)
Purpose of the 3-Tier Model
    • Introduced as an initial framework to support upgrade-safe customer extensions.
    • Useful to understand the evolution toward the Clean Core layered approach.
    • Existing customer code designed according to this model:
        ◦ Does not automatically require migration, especially Tier-2 wrappers.
The Three Tiers Explained
Tier 1 — ABAP Cloud
    • Preferred and future-proof approach.
    • Intended for all new development.
    • Characteristics:
        ◦ Restricted, cloud-optimized ABAP
        ◦ Access to released SAP APIs only
        ◦ Upgrade-safe by design
Tier 2 — Cloud API Enablement
    • Acts as a bridge layer.
    • Used to:
        ◦ Wrap existing Tier-3 customer code
        ◦ Wrap SAP standard objects not yet released for Tier-1
    • Goal:
        ◦ Provide a stable, reusable API consumable from Tier-1
Tier 3 — Classic ABAP
    • Legacy approach.
    • Used for:
        ◦ Existing code
        ◦ Deep or complex extensions not possible in Tier-1
    • Characteristics:
        ◦ Tightly coupled to SAP core
        ◦ High upgrade risk
    • Recommended only as a last resort
Status
    • The 3-Tier model has been retired (sunset).
    • Replaced by a more flexible and pragmatic Clean Core layered model.

Second Generation: Clean Core Layered Concept
Evolution Toward a More Flexible Model
From Binary to Risk-Based Clean Core
    • Early Clean Core messaging was perceived as:
        ◦ All-or-nothing
    • Practical challenges:
        ◦ Some non-released APIs are stable in reality
        ◦ Removing all existing custom code is unrealistic
    • SAP response:
        ◦ Shift to a risk-oriented, layered approach
        ◦ Clean Core becomes a roadmap, not a rigid rule

Overview of the Clean Core Extensibility Model
Core Objectives
Transparency and Technical Debt Reduction
    • The model introduces:
        ◦ Four Clean Core levels (A–D)
        ◦ Level A represents the highest quality
    • Key principles:
        ◦ Customers should aim for the highest feasible level
        ◦ Higher levels:
            ▪ Reduce technical debt
            ▪ Simplify upgrades
            ▪ Align with SAP best practices
    • Classification rule:
        ◦ An extension is rated by the least qualified technology used

Benefits of the Layered Clean Core Concept
Improvements Over the 3-Tier Model
Pragmatic Classification
    • Provides granular differentiation between:
        ◦ Upgrade-stable extensions
        ◦ Risky extensions
Re-evaluation of Classic ABAP
    • Classic ABAP objects are not automatically high risk.
    • Risk is assessed contextually.
Balanced Perspective
    • Recognizes:
        ◦ Value of legacy code
        ◦ Importance of modern, decoupled extensions
    • Encourages gradual modernization.

How the Clean Core Levels Work
Clean Core Levels Overview
Level A — Released APIs (Clean Core)
Level A Overview
    • Highest extensibility standard
    • Maximum upgrade stability
    • Fully aligned with SAP Clean Core vision
Coverage
    • Uses only:
        ◦ Released SAP APIs
        ◦ Released extension points
    • Applies to:
        ◦ Side-by-side extensions on SAP BTP
        ◦ On-stack extensions in SAP S/4HANA
    • On-stack development requires:
        ◦ Key User or Developer extensibility tools
        ◦ Appropriate ABAP Cloud language versions
    • Does not cover the full functional scope of Private Edition.
SAP Involvement
    • Objects are:
        ◦ Officially released
        ◦ Governed by stability contracts
    • Discoverable via:
        ◦ SAP Business Accelerator Hub
        ◦ Cloudification Repository
        ◦ SAP system metadata
Relation to Public Edition
    • Level A aligns with SAP S/4HANA Cloud Public Edition.
    • On-stack extensions from Private Edition:
        ◦ Usually require adaptation for Public Edition
    • Side-by-side extensions:
        ◦ Have higher portability due to decoupling
    • Full parity is not guaranteed.

Level B — Use of Classic APIs
Level B Overview
    • Addresses requirements not met by released APIs alone.
    • Uses:
        ◦ Well-established, documented classic APIs
    • Provides:
        ◦ Broader customization scope than Level A
        ◦ Low upgrade risk
Eligibility
    • Extensions qualify when using:
        ◦ Released APIs
        ◦ Classic APIs only
    • Includes:
        ◦ Wrappers around classic APIs (e.g. BAPI_PO_CREATE1)
        ◦ Classic ABAP extensions (Dynpro, Web Dynpro, ALV)
        ◦ Custom objects using Standard ABAP without restricted SAP objects
SAP Involvement
    • Classic APIs:
        ◦ Explicitly named by SAP experts
        ◦ No formal stability contracts
    • Identified primarily via:
        ◦ Cloudification Repository
    • Best alternative when released APIs are unavailable.

Level C — Use of Internal Objects
Level C Overview
    • Uses SAP internal objects not intended for customer use.
    • Characteristics:
        ◦ No formal support
        ◦ Incomplete or missing documentation
        ◦ No stability guarantees
    • Enables advanced capabilities with manageable risk.
Eligibility
    • Applies when using:
        ◦ Objects not classified as Level A or B
    • Examples:
        ◦ Internal function modules
        ◦ Internal classes
        ◦ Read-only access to non-approved SAP tables
SAP Involvement
    • Internal objects may:
        ◦ Change without notice
        ◦ Be reclassified to Level B or D over time
    • Reclassification depends on:
        ◦ Customer feedback
        ◦ Product strategy
        ◦ Observed upgrade issues
SAP Object Changelog
    • Introduced to manage Level C risk.
    • Provides:
        ◦ Automated code analysis
        ◦ Early visibility of incompatible changes
        ◦ Better upgrade planning
    • Encourages refactoring toward Levels A or B.

Level D — Unclean Core
Level D Overview
    • Highest risk category
    • Causes:
        ◦ Severe technical debt
        ◦ High maintenance effort
        ◦ Upgrade instability
    • Strongly recommended:
        ◦ Immediate remediation
Eligibility
    • Applies when using:
        ◦ Objects explicitly marked as not recommended
    • Examples:
        ◦ Direct write access to SAP core tables
        ◦ Modifications
        ◦ Implicit enhancements
        ◦ Use of “noAPI” objects
SAP Involvement
    • Objects explicitly classified as non-recommended.
    • Identifiable via:
        ◦ Cloudification Repository
        ◦ Status filter: noAPI
    • Provides transparency to:
        ◦ Detect
        ◦ Eliminate
        ◦ Prevent high-risk extensions

Key Exam Takeaways
What You Must Recognize Instantly
    • Clean Core is risk-based, not binary.
    • Level A is the strategic target.
    • An extension’s level is determined by its weakest component.
    • SAP actively provides tooling (Cloudification Repository, changelog) to manage risk.
Typical Exam Traps
    • ❌ Assuming classic ABAP is always forbidden
    • ❌ Treating Clean Core as all-or-nothing
    • ❌ Ignoring Level C risk management mechanisms
Correct Exam Perspective
    • Clean Core is a controlled modernization path
    • Balance innovation, legacy, and upgrade safety
    • Always aim to move upward across levels over time


Setting Up For Clean Core Development
Passaggi utili per eseguire efficacemente lo sviluppo di Clean Core

Per eseguire efficacemente un lavoro di sviluppo basato sui livelli sono utili diverse informazioni:

È necessario creare componenti software e assegnare pacchetti ad essi.
È necessario assegnare autorizzazioni di sviluppatore.
È necessario utilizzare le varianti ABAP Test Cockpit Check.
Le versioni del linguaggio ABAP devono essere assegnate agli oggetti di sviluppo.

Per configurare un sistema SAP S/4HANA Cloud Private Edition per lavori di sviluppo basati sui livelli, vengono considerati i seguenti fattori:

Configurazione iniziale
Comprensione dello stato di rilascio, dei contratti di rilascio e della visibilità dell'utilizzo
Comprendere le autorizzazioni degli sviluppatori
Comprensione dei controlli della cabina di pilotaggio di prova ABAP
Configurazione iniziale
La configurazione iniziale comprende quanto segue:

Configurazione dei componenti software
Utilizzando il report RSMAINTAIN_SWCOMPONENTS, disponibile a partire dalla piattaforma ABAP 2022, gli amministratori possono creare e configurare componenti software. I componenti software creati saranno classificati come "ABAP Cloud" o "ABAP Classic", insieme alla trasportabilità (trasportabile o locale).

Tutti gli oggetti creati in un componente software del tipo ABAP Cloud devono seguire il modello di sviluppo ABAP Cloud. Al contrario, gli oggetti nei componenti software del tipo ABAP classic possono essere di qualsiasi tipo. I componenti software basati su ABAP Cloud si mappano efficacemente al livello core pulito "A" e i componenti software basati su ABAP Classic si mappano rispettivamente ai livelli "B", "C" e "D".

Pacchetto Struttura
Per facilitare la strutturazione dei progetti software dei clienti, è necessario creare un pacchetto strutturale per ogni componente software creato dal cliente.

Pacchetti di sviluppo

Sotto i pacchetti strutturali è possibile creare uno o più pacchetti di sviluppo (a seconda delle esigenze individuali del progetto) per contenere tutti gli artefatti di sviluppo necessari.

Autorizzazioni

Ci sono alcuni oggetti di autorizzazione di cui prendere nota. Innanzitutto, per gli amministratori che configurano componenti software, è necessario l'oggetto di autorizzazione S_CTS_ADMI.

In secondo luogo, se i clienti desiderano limitare gli sviluppatori solo allo sviluppo di livello A, o se alcuni sviluppatori lavoreranno nel livello A mentre altri lavoreranno nei livelli B, C e D, allora l'oggetto di autorizzazione S_ABPLNGVS può essere utilizzato per progettare le autorizzazioni appropriate per gli sviluppatori. La procedura è la seguente:

Utilizzando il codice di transazione SACF, attivare i controlli di autorità utilizzando l'oggetto di autorizzazione S_ABPLNGVS.
Crea due ruoli. Un ruolo sarà assegnato agli sviluppatori che sono limitati solo allo sviluppo di livello A. L'altro sarà assegnato agli sviluppatori autorizzati a sviluppare a tutti gli altri livelli (ad esempio B, C o D), se applicabile al cliente. Entrambi i ruoli possono essere creati utilizzando il codice di transazione PFCG e utilizzando il ruolo SAP_BC_ABAP_DEVELOPER_5 come modello per la copia. Questo ruolo contiene l'oggetto di autorizzazione S_ABPLNGVS.

Mantenere il campo di autorizzazione ABP_LNG_VS per ogni singolo sviluppatore. Per gli sviluppatori che svilupperanno solo nel livello A, il valore da mantenere è ABAP For Cloud Development. Per tutti gli altri sviluppatori, il valore è Tutte le attività (cioè i livelli B, C o D).

Varianti di controllo della cabina di pilotaggio di prova ABAP

Esistono diverse varianti di controllo ABAP Test Cockpit con cui uno sviluppatore dovrebbe avere familiarità. Due di particolare importanza sono:

ABAP_CLOUD_DEVELOPMENT_DEFAULT
Questa variante può essere utilizzata per confermare che il codice ABAP è conforme al cloud. Con questa variante di controllo è possibile applicare le regole di base di ABAP Cloud.

ABAP_CLOUD_READY
Questa variante può essere utile quando si controlla il codice per vedere se è "ABAP Cloud ready". Controlla che vengano sviluppati solo i tipi di oggetti disponibili in ABAP Cloud, che vengano utilizzate solo le istruzioni del linguaggio ABAP Cloud e che vengano chiamate solo le API SAP rilasciate. Quando si utilizza questa variante, verrà visualizzato un elenco di lavoro dei risultati dell'ATC che descrive in dettaglio i problemi che dovranno essere risolti. A seconda del problema, è possibile utilizzare la funzionalità "Quick Fix" per adattare immediatamente il codice.

Configurazione della variante di controllo ATC per controlli del nucleo pulito
Oltre alle due varianti sopra indicate, i clienti possono creare una variante personalizzata su misura per le nuove linee guida a livello di core pulito (ad esempio API rilasciate, API classiche, ecc.) che verificherà l'utilizzo degli oggetti standard SAP in base a tali linee guida. Una volta utilizzato, il risultato ATC mostrerà quanto segue:

API rilasciate: Livello A: Nessun risultato in ATC.
API classiche: Livello B: Priorità 3 (Messaggio informativo).
Oggetti interni: Livello C: Priorità 2 (Messaggio di avviso).
Non consigliato: Livello D: Priorità 1 (Messaggio di errore).
Creare questa variante personalizzata è semplice. Basta eseguire i seguenti passaggi:

Copia la variante ABAP_CLOUD_DEVELOPMENT_DEFAULT elencata sopra in una variante con nome nuovo.
Aggiungere a quella variante appena denominata i seguenti controlli ATC aggiuntivi:
Tecnologie di miglioramento SAP consentite
Utilizzo delle API
Dichiarazioni critiche
Cerca le modifiche dei clienti
Analizzatore di vulnerabilità del codice (CVA) (se CVA è concesso in licenza di conseguenza)
Per ulteriori informazioni su come gli strumenti di sviluppo ABAP per Eclipse offrono diverse funzionalità per supportare le attività di sviluppo con un core pulito, consulta il blog: Raccomandazioni ABAP Test Cockpit (ATC) per la governance dello sviluppo ABAP con core pulito.

Stato di rilascio, contratti di rilascio e visibilità dell'utilizzo

Nel corso abbiamo accennato spesso all'importanza delle API rilasciate. La conformità Clean Core Level A richiede l'utilizzo esclusivo delle API rilasciate. Come discusso in precedenza, gli aggiornamenti software con software cloud avvengono regolarmente e le estensioni progettate e implementate al livello A non incontreranno alcuna interruzione per i clienti durante l'aggiornamento.

Per facilitare la stabilità e la trasparenza, gli oggetti di sviluppo destinati ad essere utilizzati con lo sviluppo di estensioni vengono rilasciati esplicitamente e mantenuti anche con un contratto di rilascio e una visibilità d'uso. Tutte e tre le opzioni vengono mantenute contemporaneamente sullo stesso schermo.

Le opzioni che devono essere mantenute sono le seguenti

Stato di rilascio
Questo parametro indica che l'oggetto di sviluppo è "rilasciato" (cioè disponibile per l'utilizzo).

Contratti di rilascio
Estendere (C0)
A un oggetto di sviluppo abilitato per l'estensibilità è assegnato il contratto di rilascio Extend (C0). A seconda del tipo di oggetto in questione, potrebbero esserci prerequisiti aggiuntivi prima di poter definire i punti di estensione.

Utilizzare il sistema internamente (C1)
Questa designazione si riferisce agli oggetti di sviluppo utilizzati per il consumo. L'assegnazione di C1 è richiesta per qualsiasi oggetto di sviluppo utilizzato in un'implementazione di estensione se l'obiettivo è il livello A del core pulito.

Setting Up for Clean Core Development — Exam Summary
Practical Steps for Effective Clean Core Development
Core Preparation Requirements
    • To work effectively with a Clean Core, level-based approach, the following must be configured:
        ◦ Software components and package assignment
        ◦ Developer authorizations
        ◦ ABAP Test Cockpit (ATC) check variants
        ◦ ABAP language versions for development objects

System Setup for Level-Based Development
Configuration Areas to Consider
Key Setup Dimensions
    • Initial system configuration
    • Release status, release contracts, and usage visibility
    • Developer authorizations
    • ABAP Test Cockpit governance

Initial Configuration
Software Component Configuration
Software Components and Clean Core Levels
    • Administrators create software components using report:
        ◦ RSMAINTAIN_SWCOMPONENTS (available from ABAP Platform 2022)
    • Software components are classified as:
        ◦ ABAP Cloud
        ◦ ABAP Classic
    • Transportability is defined:
        ◦ Transportable
        ◦ Local
Mapping to Clean Core Levels
    • ABAP Cloud components
        ◦ Must follow the ABAP Cloud development model
        ◦ Map directly to Clean Core Level A
    • ABAP Classic components
        ◦ Allow unrestricted ABAP usage
        ◦ Map to Clean Core Levels B, C, and D

Package Structure
Structural Packages
    • One structural package should be created per customer software component.
    • Used to organize development artifacts consistently.
Development Packages
    • One or more development packages are created under the structural package.
    • Contain all development artifacts required by the project.

Developer Authorizations
Required Authorization Objects
Administrative Authorization
    • For software component configuration:
        ◦ Authorization object: S_CTS_ADMI

Restricting Developers by Clean Core Level
Language Version Authorization
    • Authorization object:
        ◦ S_ABPLNGVS
    • Enables restriction of developers to:
        ◦ Level A only
        ◦ Or Levels B, C, and D
Authorization Setup Procedure
    • Activate authority checks using transaction:
        ◦ SACF
    • Create two roles using transaction:
        ◦ PFCG
    • Use role template:
        ◦ SAP_BC_ABAP_DEVELOPER_5
Authorization Field Configuration
    • Maintain authorization field ABP_LNG_VS:
        ◦ ABAP for Cloud Development → Level A developers
        ◦ All Activities → Developers allowed in Levels B, C, D

ABAP Test Cockpit (ATC) Variants
Standard ATC Variants
ABAP_CLOUD_DEVELOPMENT_DEFAULT
    • Validates:
        ◦ Basic ABAP Cloud compliance
    • Ensures:
        ◦ Use of cloud-compatible language constructs
ABAP_CLOUD_READY
    • Used to assess whether code is:
        ◦ ABAP Cloud ready
    • Checks:
        ◦ Allowed object types
        ◦ ABAP Cloud language usage
        ◦ Use of released SAP APIs only
    • Provides:
        ◦ ATC worklist
        ◦ Quick Fix options where applicable

Custom ATC Variant for Clean Core Levels
Purpose
    • Enforces Clean Core level governance across customer code.
ATC Result Classification
    • Released APIs → Level A → No ATC findings
    • Classic APIs → Level B → Priority 3 (Information)
    • Internal Objects → Level C → Priority 2 (Warning)
    • Not Recommended Objects → Level D → Priority 1 (Error)

Creating the Custom Variant
Configuration Steps
    • Copy variant:
        ◦ ABAP_CLOUD_DEVELOPMENT_DEFAULT
    • Add the following ATC checks:
        ◦ Allowed SAP enhancement technologies
        ◦ API usage
        ◦ Critical statements
        ◦ Search for customer modifications
        ◦ Code Vulnerability Analyzer (CVA), if licensed

Release Status, Contracts, and Usage Visibility
Purpose
    • Ensures:
        ◦ Upgrade stability
        ◦ Transparency
        ◦ Contractual guarantees for extension development

Release Status
Released Objects
    • Indicates that an object:
        ◦ Is officially released
        ◦ May be used in extensions

Release Contracts
Extend (C0)
    • Assigned to:
        ◦ Objects enabled for extensibility
    • Required to:
        ◦ Define extension points
Use System Internally (C1)
    • Required for:
        ◦ Objects consumed by extensions
    • Mandatory for:
        ◦ Clean Core Level A compliance

Usage Visibility
Visibility Options
    • Use in Key User Apps
        ◦ For objects intended for key user extensibility
    • Use in Cloud Development
        ◦ For objects intended for on-stack developer extensibility

Key Exam Takeaways
What You Must Recognize Instantly
    • Clean Core development requires governance, not just coding discipline.
    • Software components and language versions directly map to Clean Core levels.
    • ATC is the central enforcement mechanism.
    • Released APIs + C1 contract + proper visibility are mandatory for Level A.
Typical Exam Traps
    • ❌ Assuming Clean Core is enforced automatically
    • ❌ Ignoring language version restrictions
    • ❌ Using ATC without Clean Core–specific variants
Correct Exam Perspective
    • Clean Core is enabled through:
        ◦ Structural setup
        ◦ Authorizations
        ◦ Tooling enforcement
    • Proper setup determines what developers are allowed to do, not just what they should do
